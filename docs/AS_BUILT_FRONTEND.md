# Zoryx — As-Built Reference (Frontend)

Covers `pos-frontend/` only — the single React POS admin SPA in this repo. See [AS_BUILT_BACKEND.md](./AS_BUILT_BACKEND.md) for the API it talks to, the overview, the feature-status matrix (§8), known problems (§13), and could-not-determine notes (§15), which cover both apps.

Stack: React 19, Vite 8, TypeScript, Tailwind v4, react-router-dom v7, @tanstack/react-query v5, axios, socket.io-client, recharts. Full dependency table in Appendix B. Generated by reading the code as of 2026-10-27; claims cited `file:line` (paths relative to `pos-frontend/`) where non-obvious; unconfirmed claims tagged `(inferred)`.

**KITCHEN special case**: never appears in `NAV_ITEMS`; its only route is `/kitchen-display`, declared outside `<Route element={<AppLayout />}>` so it gets no sidebar/topbar/mobile shell. `getHomeRoute()` (`src/routes/homeRoute.ts`) special-cases KITCHEN straight to `/kitchen-display`; every other role's home is the first `NAV_ITEMS` entry it can access.

**ORDER_TAKER special case** (same treatment as KITCHEN, added for the order-taker mobile screens): also never in `NAV_ITEMS`. `/take-order` and `/my-orders` are declared outside `AppLayout`, nested under one layout route whose element is `<ProtectedRoute allowedRoles={["ORDER_TAKER"]}><TakerShell /></ProtectedRoute>` (`src/App.tsx`) — a single role check and shell wrapping both routes via `<Outlet/>`, rather than wrapping each route individually. `getHomeRoute()` special-cases `ORDER_TAKER` straight to `/take-order`. `TakerShell.tsx` (`src/components/TakerShell.tsx`) is this role's entire shell: a compact top bar (logo, staff name, Log out, a Live/Reconnecting/Offline connection pill) and a two-tab bottom nav ("New order"/"My orders") — no sidebar, no `BusinessDayBar`, no admin nav. It owns `TakerOrdersProvider` (`src/context/TakerOrdersContext.tsx`), which connects one socket for the session (no `"join"` emit needed — the backend auto-joins an ORDER_TAKER socket to `user:<staffId>` on connect) and listens for `order:accepted`/`order:rejected`/`order:status`, invalidating the orders list/detail queries on each and firing a chime (`useChime`, see below) plus `navigator.vibrate` where supported. Any URL outside these two bounces back to `/take-order` via the existing `ProtectedRoute` → `/` → `RootRedirect` → `getHomeRoute` chain — no new redirect logic was needed for that.

**ProtectedRoute** (`src/routes/ProtectedRoute.tsx`): not authenticated → `Navigate to="/login"` with `state={{from: location}}`; authenticated but role mismatch → `Navigate to="/"` (which bounces through RootRedirect to that role's own home, **not** back to login).

`TopBar.tsx` (desktop only): `BusinessDayBar` + staff name + Log out. **End day with scheduled orders on hold:** when the server answers 409 `SCHEDULED_ORDERS_PENDING`, `BusinessDayBar` opens a `Modal` listing them (number and time) with three choices. "Keep the day open" closes it. "Cancel all and end day" cancels each, conditional on still being scheduled, then retries End day, where the usual open-orders confirm still applies. "Release all now" releases each, then explains they're live in Incoming orders and must be accepted or rejected before the day can end, and navigates there. One already released by the job counts as done for release, and is reported for cancel.

**Mobile shell** (below 768px, `src/routes/mobileShell.ts` + `src/components/shell/*`): AppLayout switches purely by CSS breakpoint, not separate routing.

### 7.2a ONLINE_ADMIN

`ONLINE_ADMIN` runs the customer website's content and reviews online orders — nothing else. It sees exactly two things in the shared shell: the **Online store** group (six pages, §7.3a) and **Incoming Orders**. `getHomeRoute("ONLINE_ADMIN")` returns **`/online-store/menu`** (an explicit case, like KITCHEN and ORDER_TAKER); Categories and Kitchens, which it could open before, were removed from its roles so "everything else" is hidden both in the nav and by `ProtectedRoute`. On mobile its bottom tabs are its first four destinations (Incoming Orders, Menu photos and names, Store settings, Delivery areas) and the rest sit under "More". `BusinessDayBar` already renders nothing for it.

**What changed on the backend to make Incoming Orders work for it** (the screen existed only for reception): `GET /orders/incoming`, `POST /orders/:id/accept` and `POST /orders/:id/reject` now admit ONLINE_ADMIN, **scoped to `source: ONLINE`** (other sources are a 404, as if they didn't exist) and `accept` refuses a `discount` (403 — it changes a price); `config/socket.ts` lets it join the listen-only `pos-admin` room so the badge and chime update live (kitchen rooms stay closed). On the frontend this means: `IncomingOrdersContext` is active for it and ignores `order:submitted` events from other sources; `IncomingOrdersPage` hides the source filter chips and the order-change-request panel (and never polls that endpoint — `useIncomingOrderChanges(enabled)`); `IncomingOrderCard` doesn't offer the Discount field or the Edit button.

### 7.4 Session handling and 401/403 behavior

`src/auth/session.ts`: localStorage key `"zoryx:staff-session"`, stored shape `{ staff: {id, name, username, role, kitchenId}, token }`. `getStoredSession()` wraps `JSON.parse` in try/catch, returning `null` on any failure.

`src/api/client.ts`: axios instance, `baseURL: import.meta.env.VITE_API_URL`. Request interceptor attaches `Authorization: Bearer <token>` when one exists. Response interceptor's 401 handling, quoted:
```ts
if (axios.isAxiosError(error) && error.response?.status === 401) {
  const hadToken = Boolean(error.config?.headers?.Authorization);
  if (hadToken) {
    clearStoredSession();
    window.dispatchEvent(new Event("auth:logout"));
    if (window.location.pathname !== "/login") {
      window.location.assign("/login");
    }
  }
}
```
A 401 is only treated as "session expired" when the failing request **carried** a token — a bad-login-credentials 401 (no token attached) is left alone and surfaces normally via `getApiErrorMessage`. A real session-expiry 401 clears storage, dispatches a custom `"auth:logout"` window event (consumed by `AuthContext` to sync React state), and forces a **hard navigation** (`window.location.assign`, not router `navigate()`) to `/login`.

**403**: no interceptor logic at all — every 403 rejects normally and is handled per-call wherever a page chooses to catch it (e.g. `BusinessDayBar.tsx` specifically inspects a **400** body for `orderIds` to offer the force-end confirm — nothing globally handles 403 with a redirect or toast).

`src/context/AuthContext.tsx`: React state initialized lazily from `getStoredSession()`; listens for `"auth:logout"`; exposes `{staff, token, isAuthenticated, login, logout}`.

### 7.5 Data fetching / state approach

`@tanstack/react-query` v5 is the **only** server/global-state library — no redux/zustand/mobx/recoil/jotai in `package.json`. Local UI state is plain `useState`/`useRef`/React Context (AuthContext only).

`src/hooks/createCrudHooks.ts`: generic factory returning `{useList, useCreate, useUpdate, useRemove}`; every mutation invalidates the same query key on success (list-only invalidation, no optimistic updates/cache merging) — used by Categories, Kitchens, DiningAreas, Employees, InventoryItems, InventoryLinks, MenuItems, Deals, Vendors-style resources.

Query key conventions: simple flat resources use a single key (`["dashboard"]`, `["kitchen-queue", kitchenId]`); list+detail resources use 2-3 segment arrays (`["orders","list",filter]`, `["orders","detail",id]`). Some hooks hand-roll `useQuery`/`useMutation` instead of `createCrudHooks` (`useOrders.ts`, `useVendors.ts`, `useBusinessDay.ts`, `useDashboard.ts`, `useKitchenQueue.ts`). `useBusinessDay.ts` is the one hook using cache-write-through (`setQueryData`) instead of invalidation, since start/end-day mutations return the exact new "current" object. Single-record mutations (orders, vendors) do `invalidateQueries(["x","list"])` + `setQueryData(["x","detail",id], result)` to patch an open detail view in place.

### 7.6 Socket.io client usage

`src/socket/client.ts`:
```ts
export function connectSocket(token: string): Socket {
  return io(import.meta.env.VITE_API_URL, { auth: { token } });
}
```
A fresh connection per caller, not a shared singleton — by design, since no consumer needs the connection to outlive its own screen/shell.

**Consumer 1**: `src/pages/KitchenDisplayPage.tsx`. Lifecycle: effect runs only when `kitchenId && token` are both present → `connectSocket(token)` → `socket.emit("join", "kitchen:<id>", ackCallback)`, surfacing any join error into a visible banner. Listens for:
- `connect_error` → sets a banner "Live updates disconnected: ‹message›. Reload the page to reconnect." (needed because socket auth failures don't go through the axios 401 interceptor — sockets aren't HTTP).
- `order-item:new` → maps payload items onto a synthetic `order: {orderNumber, diningArea}` field, prepends to local state, de-duped by id.
- `order-item:note-updated` (same payload shape) → the same mapping, but **replaces** any existing card for those ids and moves them to the top, then adds the ids to a local `noteUpdatedIds` set (the "Note updated" flag). The flag clears when that item's status advances, from this screen or via `order-item:updated`. Items the screen didn't have yet (e.g. a `READY` one after a reload) are added.
- `order-item:updated` → ignored if `payload.kitchenId !== kitchenId` (defensive client-side filter even though the room join already scopes this), else patches `status` on the matching local row.

Cleanup on unmount/dependency change: `socket.off(...)` all four + `socket.disconnect()`.

**Reconnect/missed-event recovery for KitchenDisplayPage: none.** Default socket.io-client auto-reconnect is left as-is, but there is no re-fetch of the queue on reconnect, no re-join confirmation beyond the original join ack, and no event-sequence tracking to recover anything missed while disconnected. `useKitchenQueue` seeds local `items` state from a REST snapshot exactly once on mount; after that, local state is the only source of truth until a full page reload.

**Consumer 2** (`order:submitted` now also invalidates `["orders", "scheduled"]`, so a scheduled order released by the server's job leaves the Scheduled list at once, and its toast reads "(scheduled order released)" for a `POS`-sourced order instead of the old fallback "online"): `src/context/IncomingOrdersContext.tsx` (`IncomingOrdersProvider`, mounted once in `AppLayout`, alive for every POS_ADMIN/SUPER_ADMIN page). Connects when `staff.role` is POS_ADMIN/SUPER_ADMIN, `socket.emit("join", "pos-admin", ...)`, listens for `order:submitted` (chime + toast + refetch), `order:updated`/`order:accepted`/`order:rejected` (refetch only). Unlike KitchenDisplayPage, this one **does** re-fetch on reconnect (`connect` handler calls the same refetch as a live event) and relies on `useIncomingOrders`'s own `refetchInterval: 30_000`/`refetchOnWindowFocus` for the rest — server data always wins over any locally held state, there is no local item list to patch.

**Consumer 3**: `src/context/TakerOrdersContext.tsx` (`TakerOrdersProvider`, mounted once in `TakerShell`, alive for both `/take-order` and `/my-orders`). Connects whenever a token exists — **no `"join"` emit at all**: an ORDER_TAKER socket is auto-joined to `user:<staffId>` by the backend unconditionally on connect (see the backend doc's `config/socket.ts` notes), so there's nothing to request. Listens for `order:accepted`/`order:rejected`/`order:status`, invalidating `["orders","list"]` and that order's `["orders","detail",id]` on each, plus a chime and `navigator.vibrate(200)` (feature-detected). Also tracks three connection states (not two, like the other two consumers) — `live`/`reconnecting`/`offline` — the last one driven by the browser's own `online`/`offline` events rather than the socket alone, since `TakeOrderPage` disables "Send to reception" specifically when the device itself has no network, not just when the socket happens to be reconnecting.

**Shared chime/mute/unlock logic**: `src/hooks/useChime.ts`, extracted so `IncomingOrdersContext` and `TakerOrdersContext` don't each carry their own copy — a two-tone Web Audio oscillator chime, lazy `AudioContext` creation, a "Tap to enable sound" unlock banner when the browser has the context suspended pending a user gesture, and a `localStorage`-persisted mute (different keys per screen — a receptionist's and a waiter's mute choices are different people on different devices).

### 7.6a Guest orders — how staff screens read them

A guest-checkout order has **no `Customer` row**, so every screen that shows who an order is for goes through one helper, `src/lib/orderCustomer.ts` → `getOrderCustomer(order)`. It returns `{ name, phone, addressLines, areaName, deliveryFee, code }`, reading the `Customer` relation first and falling back to the Order's own `customerName`, `customerPhone`, `deliveryAddress` (split on newlines into lines), `deliveryArea.nameEn`, `deliveryFee` and `publicCode`. It accepts both an `OrderDetail` and the list endpoint's bare `OrderSummary` (every relation is optional). Used by the Incoming card, Order detail, the Orders list's `OrderCustomerCell`, the receipt builders and the kitchen slips — so they can't drift apart.

**Payment proof.** The proof is private, so the backend serves it only to a signed-in staff member (`GET /api/pos/orders/:id/payment-proof`) and an `<img src>` can't send the Authorization header. `ordersApi.getPaymentProof` fetches it as a blob through the app's authenticated client, `useProofImageUrl` turns it into an object URL (revoked on unmount, re-fetched when `paymentProofMediaId` changes, i.e. when the customer replaces it) and `components/PaymentProof.tsx` renders the thumbnail plus a full-size modal. Orders placed before proofs moved to Postgres have a `paymentScreenshotUrl` under `/uploads`; `PaymentProof` falls back to that public URL for them.

**Order types updated** (`api/orders.ts`): `OrderBase` gains `customerName`, `customerPhone`, `deliveryAreaId`, `deliveryFee` (string; already included in `totalAmount`), `publicCode`, `paymentProofMediaId`; `OrderDetail` gains `deliveryArea`. `ordersApi` gains `markDelivered` and `getPaymentProof`.

**Order-taker display status.** `takeOrder/deriveDisplayStatus.ts` now maps `COMPLETED` to "Served" — an order marked delivered is finished whatever its items' own statuses say (before, `COMPLETED` could never occur, so it fell through to the item logic).

**End Day.** The "end the business day anyway?" prompt in `BusinessDayBar` now reads "awaiting reception, pending, confirmed, in kitchen, or ready — not yet marked delivered", matching the backend's blocking statuses (`CONFIRMED` was added so accepted-but-undelivered online/guest orders can't be silently left behind).

### 7.7 Printing

`src/components/PrintStyles.tsx` — shared `<style>`, tuned for an **80mm thermal roll**: `@page { size: 80mm auto; margin: 0; }`, monospace font (`Courier New`) for aligned columns at small size, dashed (`border-bottom: 1px dashed #000`) rather than solid table rules (renders more reliably on a thermal head), `.ticket { page-break-after: always }` / `:last-child { page-break-after: auto }` for one physical page per kitchen ticket, `.no-print` hidden under `@media print`.

- **Both print pages refuse a `SCHEDULED` order:** no auto-print, just "This order is scheduled and on hold — nothing prints until it's released." A released scheduled order's receipt and kitchen tickets (`buildReceiptDoc`/`buildKitchenTicketDocs`) carry a "Scheduled for …" line, bold and double height on the ticket.
- **PrintReceiptPage.tsx**: fetches the order, auto `window.print()` once on load (`hasPrintedRef` guard). Renders: "Receipt" header, order number + status, timestamp, type, dining area or delivery address, a table of non-deal items (deal-exploded `unitPrice:"0"` lines filtered out) + one row per deal line, each with its note as "Note: …" under the name, then discount/total/payment method. Manual re-print button.
- **PrintKitchenTicketsPage.tsx**: fetches the order and kitchens, prints once both have loaded, and renders `buildKitchenSlips(order, kitchens, { added })`. That's one `.ticket` (one physical page) per kitchen with items, laid out exactly like the direct print in §7.7a: a big "THIS KITCHEN: …" header between double rules, the order lines, this kitchen's group in bold 15px, then "Other kitchens" in 11px with a label per kitchen. Long names and notes wrap (`word-break`) inside the 80mm page. `?added=` comes from the fallback link offered when a direct print fails, so ADDED marks survive the fallback.

Both pages still exist unchanged, as the fallback below — opened via `window.open(url, "_blank")`.

### 7.7a Direct-to-printer (ESC/POS via print-agent)

`OrderDetailPage.tsx` has three print buttons — "Print table receipt", "Print kitchen tickets", "Print final receipt" — that try direct ESC/POS printing first, through a separate standalone `print-agent/` process running on the cashier's PC (never deployed — see `docs/PRINT_PROTOCOL.md` and the backend doc's §3.16a/§5). Flow:
1. Build the doc(s) client-side: `src/print/buildReceiptDoc.ts` (one detailed, shop-branded doc — used by **both** "table receipt" and "final receipt", see below) or `src/print/buildKitchenTicketDocs.ts` (one slip per kitchen the order touches, each listing every item of the order — see "Kitchen slips" below).
2. `usePrintDocs()` (`src/hooks/usePrinter.ts`) POSTs `{printerId, docs}` to `/api/pos/print`.
3. Success → inline `role="status"` message near the buttons ("Sent to printer."). Any failure (offline 503, agent-reported 502, timeout 504) → inline `role="alert"` message **plus** an explicit "Open browser print view" button that calls `window.open(...)` to the old `PrintReceiptPage`/`PrintKitchenTicketsPage` routes (both receipt buttons fall back to the same `/print/receipt` route, since they're the same document) — deliberately not auto-opened inside the error handler, since `window.open()` after an awaited network round-trip reliably gets popup-blocked; it only fires from that button's own direct click.

No toast system exists anywhere in this app (still true) and none was added for this — the inline message reuses the same `role="alert"`/status-color-token pattern already used elsewhere on this page (`assignError`, `addItemError`, etc.), just with a success variant added. A `<StatusBadge status={online ? "ACTIVE" : "INACTIVE"} label="Printer: connected"/"Printer: offline">` sits next to the buttons, driven by `usePrinterStatus()` (`refetchInterval: 15000`) — reuses the existing component, no new UI primitive.

**Three print types, two doc builders.** "Print table receipt" and "Print final receipt" call the exact same `buildReceiptDoc(order)` — identical content (shop name/phone from `src/config/shop.ts`, order number, date/time, type + table/delivery, every item as a row with size/add-ons inline and its note on an indented "Note: …" line beneath, deal lines bold with their own note beneath and their composed items as smaller indented sub-lines (a customized deal line prints `"{qty}x {dealName} (customized)"` at its final price — same composed-items sub-lines underneath, now possibly carrying a size/add-ons), discount, a double-ruled bold total, payment method, a thank-you footer). The only difference between them is *when* a cashier clicks which: "table receipt" right after placing the order (a copy for the customer/table), "final receipt" at payment confirmation. **Kitchen slips** (`print/kitchenSlip.ts`, rendered by `buildKitchenTicketDocs.ts` for the print agent and by `PrintKitchenTicketsPage` for the browser — one model, so the two can't drift):
- **Who gets one:** every kitchen with at least one item on the order gets a slip. **Every slip lists all of the order's items**, grouped by kitchen, so each kitchen can match its dishes against the others' before the food goes to the table.
- **Header and order lines:** "THIS KITCHEN: <NAME>", centered and bold between double rules, in double width-and-height when it fits in 24 characters (half the 48-character 80mm width), otherwise double height. Then order number, table (with its area) or TAKEAWAY/DELIVERY, order type, and time placed. A released scheduled order adds "SCHEDULED FOR …", and a takeaway or delivery order adds "PACK ALL ITEMS - TAKEAWAY/DELIVERY". There is no per-item takeaway flag in the data model; see the note below.
- **This kitchen's items:** its group comes first, labelled "<Kitchen> (this kitchen)", bold and double height. Each item line reads quantity×name, size, and the deal tag "(Deal)"/"(Deal - customized)" for a deal item, as before. Add-ons go on an indented line, and each note (the item's own, plus the deal line's for a deal item) on its own indented "NOTE:" line.
- **Other kitchens' items:** under "Other kitchens", one bold "<Kitchen>:" label per kitchen, in the kitchen list's order on every slip, with items at normal size and indented.
- **ADDED marks:** `options.added` (item id → newly added quantity) marks items "[ADDED]", or "[ADDED +N]" when only part of a line is new, and adds an "ITEMS ADDED: N" header line. The marks are set on two paths:
  - **Adding items on Order Detail:** marked by new item id (`newItemQuantities`). The full slips print automatically right after the add, to every kitchen with items. The result shows under the Add item form, with the browser-print fallback link (carrying `?added=`) if the agent is offline.
  - **Approving an order-taker edit in Incoming:** approval re-creates every row, so items are matched by content (`diffAddedQuantities`: menu item, size, add-ons, note, deal). Its receipt and slips mark what the edit added.

  A reprint ("Print kitchen tickets") and the accept-time "Print and send" print the full slips without marks.
- **Paper width:** the builder clamps any text block to the 200-character protocol limit. The print agent word-wraps every line to the paper with a hanging indent (§7.7a / `docs/PRINT_PROTOCOL.md`), so nothing runs off the edge at 80mm or 58mm.
- **Takeaway marks:** the data model has no per-item takeaway flag (e.g. one dish packed from a dine-in table), so slips mark takeaway and delivery at order level only.

`src/config/shop.ts` — `{name, phone, address, currencyLabel, timeZone}`. Currently `name`/`phone` are the cafe's real values; `address` is `null` (not supplied yet — add it there when available, it's conditionally rendered on the receipt). This is the first part of the original pre-launch plan's Step 7 (shop config + money/date formatting) to actually land — `src/lib/format.ts` (`formatMoney`, `formatDateTime`, `formatTime`) was created alongside it, used only by the new print-doc builders so far; `PrintReceiptPage.tsx`/`PrintKitchenTicketsPage.tsx` are untouched and still format money/dates inline exactly as before.

`VITE_PRINTER_ID` (frontend env, defaults to `"main"`) picks which print agent `usePrinterStatus`/`usePrintDocs` target — must match `PRINTER_ID` in that agent's own `print-agent/.env`.

**Guest orders on paper.** `buildReceiptDoc` (and the browser fallback `PrintReceiptPage`) now print, under the type line, the customer's name and phone, the address — **one block per line**, so the printer wraps it cleanly and the stored newline before "Landmark:" can't break a block — and **Order code: K7P2M**; and a **Delivery fee** row above the TOTAL (which already includes it). The delivery address used to be appended to the type line; it now prints for every delivery order, POS ones included. The kitchen slip model (`KitchenSlip.customerLines`, read by both `buildKitchenTicketDocs` and `PrintKitchenTicketsPage`) carries the name and phone, the address lines and the order code for takeaway/delivery orders; **no money** is on a kitchen slip, so the fee appears on the customer receipt only. No print-agent or protocol change was needed — the builders only emit the same `text`/`row` blocks (`docs/PRINT_PROTOCOL.md` is unchanged).

`@theme` block, `src/index.css`. Notably, `index.css` imports only `tailwindcss/theme.css` + `tailwindcss/utilities.css`, **deliberately skipping Preflight** — native unstyled `<table>`/`<button>` elsewhere intentionally still look like plain HTML until migrated to the shared components.

- **Typography**: `--font-heading:"Bricolage Grotesque"` (titles only), `--font-body:"DM Sans"` (everything else). Scale: title 26px, section 20px, card-head 16px, body 15px, meta 13px, numeric 18px, display 32px (Kitchen Display only).

**`src/components/ui/` exports**: `Button`/`buttonClassName` (5 variants × 2 sizes), `Input`/`Select`/`Textarea`, `SearchInput` (new: a 44px `type="search"` field with a magnifier, `aria-label` from a required `label` prop, and its own 44px clear (×) button shown only when there's text. Enter never submits a surrounding form, Escape clears, and the browser's own cancel glyph is hidden so there's one ×), `FormActions`, `Card`, `Table`/`TableBody`/`TableCell`/`TableHead`/`TableHeaderCell`/`TableRow` (responsive "stack" vs "scroll" mode via context — scroll mode used only by the Attendance matrix), `StatusBadge` + its tone-mapping helpers (maps every backend status string, orders/items/payments/attendance, plus synthetic ones like LOW_STOCK/ACTIVE, to one of 5 quiet dot+label tones), `Modal` (native `<dialog>`, no portal lib), `ConfirmDialog` (a `Modal`-based `window.confirm` replacement — fully controlled, same philosophy as `Modal` itself: the caller owns `isConfirming`/`error` state and decides whether to close on success or keep it open with `error` set, e.g. a 409), `PageHeader`, `EmptyState`.

**`ConfirmDialog`** also takes optional `confirmVariant` (default `"danger"`) and `confirmingLabel` (default `"Deleting…"`). Both are additive, so existing callers are unchanged; the Scheduled list uses them for a green "Release now". **`ConfirmDialog` is new and is the first non-`window.confirm` destructive-action UI in this app.** Every other delete across the app (`StaffPage.tsx`, `InventoryLinksSection.tsx`, `BusinessDayBar.tsx`, `CategoriesPage.tsx`, `DiningAreasPage.tsx`, `KitchensPage.tsx`, `MenuItemsTab.tsx`, `DealsTab.tsx`, `AddOnsTab.tsx`, and the "remove order item" action on `OrderDetailPage.tsx`) still uses `window.confirm`/`window.alert`, with zero positive "it worked" feedback on success — only `InventoryItemList.tsx`'s delete (the first consumer of `ConfirmDialog`) uses it, plus a local `role="status"` success message, matching the one other precedent for this in the app (`OrderDetailPage.tsx`'s print-feedback message). Nothing else was migrated to the new dialog in this pass — only inventory's delete, which is what asked for it.

**Design-system bypass sweep**: raw `<table>` found only in `PrintReceiptPage.tsx` (expected — print views intentionally skip the admin design system). Raw lowercase `<button>` found in: tab toggles (MenuPage), icon-only cart controls (CartPanel), chip/tile selectors (ChipSelectRow, DiningAreaGrid, KitchenTabs, MenuTileGrid), bottom-sheet cart controls (NewOrderPage), print-trigger buttons, and mobile-shell chrome (BottomTabBar, MobileTopBar, MoreMenu) — all either print content, mobile chrome, or tap-target tiles/toggles that intentionally don't want the form-`Button` treatment, not accidental bypasses. Inline hex colors in `src/pages/`: **zero hits** — every page consistently uses theme-token classes.

**Other notes**: `ONLINE_ADMIN` now has its own wiring (§7.2a): the Online store section (home route `/online-store/menu`) and Incoming Orders (online orders only). `MenuItemsTab.tsx` still carries its older read-only + online-toggle-only render path for that role, but `/menu` itself is not routed to it — the Online store pages replaced that need (they edit the website fields, never prices), so that path is now unreachable and could be removed.
