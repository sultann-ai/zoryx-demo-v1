## 1. Overview

A single-location restaurant POS + online-ordering backend, in Express 5 + Prisma 6 + PostgreSQL, serving one React admin frontend. Orders from the floor (POS), phone, and (API-only) online customers all land in one `Order` table, split live to kitchen displays over Socket.io. A business day — not the calendar date — is the unit everything (order numbers, dashboards, reports) is grouped by. Deals/combos, menu-item variants (sizes), and a vendor purchase ledger exist in the schema and API but were added after the original SRS and aren't in it. There is no customer-facing web app in this repo at all — only the POS admin frontend exists; online ordering is a backend API surface with no UI consumer present. The backend also serves the customer website's non-ordering content — photos stored in Postgres, Urdu names, shop info, delivery areas, payment accounts, gallery, testimonials (§3.18) — and **guest checkout**: a customer orders without an account, through reception (§3.19). No automated tests exist anywhere in the repo.

**Repo layout**
```
zoryx-demo/
├── backend/       Express + Prisma + PostgreSQL API (this document)
├── pos-frontend/      React POS admin SPA (see AS_BUILT_FRONTEND.md) — the only frontend

### 2.3 Constraints/indexes/defaults that affect behavior

- `Order` has `@@unique([businessDayId, orderNumber])` — order numbers are only unique per business day, not globally; order #1 exists once per business day.
- Order numbering race safety: `createOrder` takes a Postgres advisory lock keyed on `hashtext(businessDayId)` before computing `MAX(orderNumber)+1`, inside the write transaction (`backend/src/modules/order/order.service.ts:246`) — this is what actually prevents two concurrent requests from getting the same number, not the unique constraint alone (the constraint is the backstop if the lock were ever bypassed).
- `MenuItem.price` is nullable (`Decimal?`) — a sized item (variants carry real prices) or deal-only item has no standalone price. `MenuItem.slug` is unique and is the idempotent-seeding key; `sellableAlone` is a derived/cached boolean, not database-enforced against the variant prices.
- `StaffUser.username` and `StaffUser.employeeId` are unique; `AttendanceRecord` has `@@unique([employeeId, date])` (the DB-level mechanism `markAttendance`'s upsert relies on — see §4); `PayrollEntry` has `@@unique([employeeId, month, year])`.
- `DealComponent` has no database constraint enforcing "exactly one of menuItemId/variantId/(choiceCategoryId+choiceSize)" — that's an application-level invariant only (schema comment, `backend/prisma/schema.prisma:237-243`).
- Money is `Decimal(10,2)` everywhere, consistently.
- Soft-delete only exists for `StaffUser` (`isActive` flag via a dedicated service function) and `Kitchen`/`DiningArea`/`MenuItem`/`Deal` (all have `isActive`/`isAvailableIn*` booleans usable as soft-hide flags) — but the actual `DELETE` HTTP verb on most resources is a **hard delete**, guarded only by catching the FK-violation Prisma throws if children still reference the row (see §3 per-module error tables). `StaffUser`'s `DELETE` is the one exception that's a true soft-deactivate by design (`backend/src/modules/staff/staff.service.ts`).

## 3. API reference

Base URL: whatever `VITE_API_URL`/deployment points at. Two mount prefixes off the Express app (`backend/src/app.ts`): `/api/pos` and `/api/online`, plus an app-level `GET /health` (unauthenticated, `{status:"ok"}`) and `/uploads` (static-served, unauthenticated — payment screenshots). Per-IP rate limits cover staff login, customer auth, and `/api/online/*` (see §6). The app trusts Railway's proxy for real client IPs, sends `helmet` security headers, and caps JSON bodies at 100 KB (50 KB under `/api/online`) — see §6. CORS: a single dynamic-origin `cors()` call (`app.ts`) backed by `CORS_ORIGIN` (comma-separated, `*` wildcard supported) — requests with no Origin header (curl, health checks) are always allowed.

Both `pos.routes.ts` and `online.routes.ts` also expose their own scoped `GET /health` (`{status:"ok", scope:"pos"|"online"}`), both unauthenticated.

Auth middleware: `requireAuth` (staff JWT, sets `req.staff = {id, role, kitchenId}`), `requireRole(...roles)` (403 if role not in the allowed list), `requireCustomerAuth` (customer JWT, sets `req.customer = {id, type:"customer"}`). Full detail in §6.

### 3.1 `auth` — mounted at `/api/pos/auth`

| Method | Path | Auth | Notes |
|---|---|---|---|
| POST | `/login` | none | Body: `username`, `password` (both required non-empty strings). 401 `"Invalid username or password"` on any failure (not found, inactive, or bad password — same message, no information leak). 200: `{ token, staff: {id, name, username, role, kitchenId} }`. |

`POST /login` is rate limited to 10 **failed** attempts per 15 minutes per IP (successful logins don't count, since the whole cafe likely shares one public IP) — the 11th returns `429 { code: "TOO_MANY", error }`. See §6.

**Online** (`/api/online/menu`): `GET /` — no auth, rate limited, `Cache-Control: public, max-age=60`. Returns `{ categories, items }` built by the whitelist mapper `toPublicMenu` (`modules/store/publicMappers.ts`) — never raw rows. **Selected:** `isAvailableOnline: true` and `isOpenPrice: false` (an open-price item is never orderable online — a customer must never set their own price). **`items[]`:** `id, name, nameUr, description, descriptionUr, price` (string or `null`), `slug, categoryId, imageUrl` (the legacy free-text column, passed through), `image` (`{thumb, full, hasTransparency}` relative URLs plus whether it is a cut-out, or `null`), `isFeatured`, **`isNew`** (true for 14 days after the item's `createdAt`; only the flag is exposed, never the date), `sortOrder, orderable`, and `variants[]` (priced sizes only: `id, label, price, sortOrder, addOns[{id, name, price}]`). Ordered by category `sortOrder`, then item `sortOrder`, then name; uncategorised last. `orderable` is true when the item is `sellableAlone` and has a standalone price or at least one priced size — deal-only and half-configured items are listed with `orderable: false`. **`categories[]`:** `id, name, nameUr, sortOrder`, **`image`** (`{thumb, full, hasTransparency}` or `null` — when `null` the website falls back to the first item's photo), in `sortOrder`, only categories that have at least one listed item. **No longer returned (staff-only):** `kitchenId, isAvailableInPOS, isOpenPrice, minPrice, maxPrice, sellableAlone, createdAt, updatedAt`. The response used to be the bare array of raw Prisma rows; nothing consumes it yet.

`categoryId` is required (not optional) on create specifically because `AddOnPrice.size` is a bare string — without a category scope, two categories that happen to share a size label (e.g. Pizza's "Large" and Fries' "Large", both category-distinct) would make an add-on priced for one incorrectly eligible on the other. `menu.service.ts`'s `attachAddOns` is what joins an add-on onto a menu item's variants: an add-on is offered on a variant only if `addOn.categoryId === menuItem.categoryId` and the add-on has an `AddOnPrice` whose `size` equals that variant's `label`.

### 3.5 `category` — `/api/pos/categories`, POS_ADMIN/SUPER_ADMIN for writes, any staff for reads

Standard CRUD; 409 on duplicate name (create/update). **Doc correction (found while adding `AddOn.categoryId` in this step, not introduced by it):** `deleteCategory` relies on catching a foreign-key-constraint error to return the 409 below, but neither `MenuItem.categoryId` nor `DealComponent.choiceCategoryId`'s FK is actually `Restrict` — both are `SetNull` (Prisma's default for an optional relation, same class of gotcha already fixed once this pre-launch pass for `DealComponent.variant` — see the migrations table). So today, deleting a category that still has menu items or deal choice-slots referencing it **succeeds and silently nulls out every one of those `categoryId`s** instead of 409ing with `"Cannot delete category: menu items still reference it"` — that message only fires on the FK case this now coincidentally covers, deleting a category still used by an `AddOn` (`AddOn.categoryId` is correctly `onDelete: Restrict`). Not fixed here — out of scope for add-ons — but flagged for the hardening pass (plan Step 8). `PATCH /:id/online-content` (POS_ADMIN/SUPER_ADMIN/**ONLINE_ADMIN**) edits only `imageId` (a `CATEGORY` media asset id, or `null`), `nameUr` (text or `null`) and `sortOrder`; any other key, including `name`, is a 400; 404 if unknown. It responds with the category plus `image: {thumb, full} | null`; replacing or clearing the photo deletes the old asset in the same transaction, and deleting a category releases its photo too (§3.18). The existing `PUT` stays POS_ADMIN/SUPER_ADMIN only.

### 3.6 `diningArea` — `/api/pos/dining-areas`, POS_ADMIN/SUPER_ADMIN for writes, reads also open to ORDER_TAKER

Standard CRUD; `type` must be `TABLE`/`FAMILY_HALL`/`GENTS_HALL`; `capacity` optional positive int; delete 409s if orders still reference it.

`area` (optional on create and update) is the room/section the table is in, e.g. "Family Hall", "Gents Hall" or "Rooftop". It's free text, not an enum, so a new area needs no code change. `parseAreaField` (`diningArea.service.ts`) handles it:
- Not sent: the field is left unchanged.
- `null`, `""` or whitespace only: cleared to `null`.
- Otherwise: trimmed, with inner whitespace collapsed to one space.
- Over `DINING_AREA_SECTION_MAX_LENGTH` (50) characters, or not a string: 400.

The New Order table pickers build their area filter chips from the `area` values in use (frontend §7.3). `type` is unchanged and still required. Before `area` existed, `type` was how a table was put in a hall, which is why the migration backfilled from it. The two can now disagree (e.g. `type: FAMILY_HALL`, `area: "Rooftop"`); only `area` drives the pickers.

  "dealLines": [{ "id": "<deal-order-line-id>", "dealId": "...", "dealName": "Deal 06", "quantity": 1,
                  "unitPrice": "1900.00", "subtotal": "1900.00", "baseUnitPrice": "1850.00",

                    "items": [{ "menuItemId": "<other-pizza-id>", "name": "...", "variantLabel": "Large",

```
The online order route (`POST /api/online/orders`) rejects `customization` (and any bare `finalPrice`) with 400 — it always calls `parseOrderDeals` without `{ allowCustomization: true }`, so a customer can never set their own price.

**Create an order with an open-price item** (POS only) — `POST /api/pos/orders`
```json
{ "type": "DINE_IN", "paymentMethod": "CASH", "diningAreaId": "<dining-area-id>",
  "items": [{ "menuItemId": "<custom-cake-id>", "quantity": 1, "unitPrice": 1500, "notes": "Happy Birthday Ali" }] }
```
→ 201 — `unitPrice`/`subtotal` are the cashier's typed price, `isCustomPrice: true`:
```json
{ "...": "...", "totalAmount": "1500.00",
  "items": [{ "menuItemId": "<custom-cake-id>", "quantity": 1, "unitPrice": "1500.00", "subtotal": "1500.00",
              "isCustomPrice": true, "notes": "Happy Birthday Ali", "variantId": null, "addOns": null }] }
```
A normal (non-open-price) item rejects a client-sent `unitPrice` with 400, same route or not: `"menuItem <id> does not accept a client-sent unitPrice"`. The online route rejects `unitPrice` outright (`"items[0].unitPrice is not allowed here"`) and separately rejects an open-price `menuItemId` with no `unitPrice` at all (`"menuItem <id> is open-price and requires unitPrice"`) — defense-in-depth, since `GET /api/online/menu` already excludes every open-price item from what a customer can see.

**Create a delivery order** (online customer) — `POST /api/online/orders/` (multipart/form-data)
```
type=DELIVERY
paymentMethod=CASH
customerAddressId=<address-id>
items=[{"menuItemId":"<id>","quantity":1}]
```
→ 201, `source: "ONLINE"`, `status: "CONFIRMED"` (CASH branch), `paymentStatus` left at schema default (`PENDING`), `customerId` taken from the JWT.

```json

```
→ 200, `status: "CANCELLED"`, `cancelledReason` set. (No inventory restock, no socket emission — see §4.3.)

→ 400

### 3.18 Customer-website content — media, site settings, delivery areas, payment accounts, gallery, testimonials, store

Everything the customer website needs that isn't ordering. Modules: `modules/media/`, `modules/siteContent/`, `modules/store/`, plus the `online-content` endpoints on menu/category/deal (§3.4/3.5/3.8). **Media — images live in Postgres, not on disk** (Railway wipes local disk on redeploy; `/uploads` and `config/upload.ts` still hold the older payment screenshots, §13).

| Method | Path | Auth | Request | Errors | Response |
|---|---|---|---|---|---|
| POST | `/api/pos/media` | the three roles | multipart: `file` + `kind` ∈ `MENU_ITEM`, `DEAL`, `GALLERY`, `PAYMENT_QR`, `CATEGORY` (`PAYMENT_PROOF` is refused — reserved for the ordering module) | 400 missing/invalid `kind`, missing file, declared type not JPEG/PNG/WEBP, or bytes that aren't a real JPEG/PNG/WEBP; 413 over 8 MB | 201 `{id, kind, mimeType, width, height, sizeBytes, hasTransparency, createdAt, urls: {thumb, full}}` (relative paths) |
| GET | `/api/online/media/:id?size=thumb\|full` | none | `size` defaults to `full` | 400 other `size`; 404 unknown id **or a `PAYMENT_PROOF` asset** | image bytes |

- **Processing** (`common/media/processImage.ts`, `sharp`; memory upload, 8 MB). The file's *real* format is read from its bytes (a GIF/SVG/text file declared as `image/png` is a 400); inputs over ~50 megapixels are rejected. **Photos** (`MENU_ITEM`, `DEAL`, `GALLERY`, `CATEGORY`): auto-rotated from EXIF, **all metadata stripped** (EXIF, ICC), **smart-cropped to 4:3** (`attention` strategy), stored as WebP **1000×750** (quality 80) plus a **480×360** thumbnail (quality 75); quality drops in steps of 5 (floor 40) until roughly under 120 KB / 45 KB — a very noisy photo can stay a bit larger rather than fail. **Cut-out photos:** if the image has transparent pixels (an alpha channel whose minimum is below 250 — an alpha channel that is fully opaque does not count) it is **not cropped**: it is fitted inside the same 1000×750 box (`contain`), padded with transparent pixels, and encoded as **WebP with alpha** (alpha quality 100) for both the full image and the 480×360 thumbnail, with the same size targets; `MediaAsset.hasTransparency` is set to true. A photo without transparency is flattened onto white and cropped exactly as before, `hasTransparency` false. The public menu and deals responses expose the flag as `image.hasTransparency` so the website can show a cut-out contained on a plain surface. **`PAYMENT_QR`**: never cropped (a cropped QR won't scan), kept lossless as PNG, downscaled only when larger than 1200 px, transparency flattened onto white, no thumbnail.
- **Storage:** `MediaAsset` (metadata) and `MediaBlob` (bytes, same id). Bytes are `select`ed only by the serving route; no list/join ever loads them.
- **Serving** (`GET /api/online/media/:id`): `Cache-Control: public, max-age=31536000, immutable`, strong `ETag` `"<id>-<size>"`, `Content-Type`, `Content-Length`, **`Cross-Origin-Resource-Policy: cross-origin` (this route only)**. Assets never change once stored (a replaced photo gets a new id), so the ETag is derived from the id and an `If-None-Match` match answers **304 without reading the blob**. A QR asks for `thumb` and gets the full PNG. Has its own limiter (§6) and is exempt from the general `/api/online` one.
- **Replacing a photo deletes the old asset in the same transaction.** Whenever an item's/deal's `imageId`, a payment account's `qrMediaId`, or a gallery row's `mediaId` changes or is cleared, or a payment account/gallery row is deleted, `releaseMediaIfUnreferenced` (`media.service.ts`) deletes the previous asset (blob by cascade) — but only if no other menu item, deal, category, gallery row or payment account still references it (the orphan-purge job counts categories too). Attaching checks the asset exists and has the matching kind (`MENU_ITEM`→items, `DEAL`→deals, `CATEGORY`→categories, `GALLERY`→gallery, `PAYMENT_QR`→QR), else 400.
- **Orphan purge** (`orphanPurge.job.ts`, started from `server.ts`): at boot and every 6 hours, deletes assets that nothing references and that are older than 24 h (an upload the admin never attached). `PAYMENT_PROOF` is excluded.

**Online-content endpoints** (all three roles; reject unknown keys with 400): `PATCH /api/pos/menu/:id/online-content` (§3.4), `PATCH /api/pos/categories/:id/online-content` (§3.5), `PATCH /api/pos/deals/:id/online-content` (§3.8). Text fields are trimmed, `""` becomes `null`, Urdu names ≤ 120 chars, descriptions ≤ 600.

**Site settings** — `GET /api/pos/site-settings` returns the single row (created with placeholders — shop name "Zoryx" — on first boot by `ensureSiteSettings()`, and lazily if still missing). `PUT` merges the provided fields (partial update, like `PUT /staff/:id`); empty body or unknown key → 400. Fields: `shopNameEn/Ur`, `taglineEn/Ur`, `phone` (5–30 chars: digits, spaces, `+ ( ) -`), `whatsappNumber` (digits only, international format, e.g. `923001234567`; `^[1-9]\d{7,14}$`), `addressEn/Ur`, `mapUrl`, `openingHoursEn/Ur`, `announcementEn/Ur` (nullable), `onlineOrderingEnabled`, `facebookUrl`/`instagramUrl`/`tiktokUrl` (nullable). **`mapUrl` and the social URLs must be `http(s)`** — they become links on the public site, so `javascript:`/`data:` are rejected.

**Lists** — each is `GET /` (all rows, active and inactive, in `sortOrder`), `POST /`, `PUT /:id` (partial), `DELETE /:id` (204); unknown id → 404; unknown body key → 400. **The caps count *active* rows only** and return **409** when exceeded — on create and when re-activating an inactive row (deactivated rows don't count); checked inside a transaction, so two simultaneous creates could in principle slip one past the cap (admin-only, low risk).

### 3.19 Guest checkout — ordering without an account

A customer orders from the website with no account. The order lands in the **existing Incoming Orders inbox as `AWAITING_RECEPTION`**, exactly like any online order: nothing reaches a kitchen and no stock moves until reception accepts. Modules: `modules/guestOrder/` (routes, controller, service, and the pure validators/mappers), plus extensions to `createOrder` (§4.1). **Pricing is never duplicated** — guest orders go through the same `parseOrderItems` / `parseOrderDeals` and the same server-side pricing as every other order; the client sends no prices.

**`POST /api/online/guest-orders`** — public, JSON, not behind `ENABLE_CUSTOMER_ACCOUNTS`. Body (every other field is rejected with 400):
`{ clientRequestId (uuid), items, deals, customer: { name, phone, deliveryAreaId, house, street, landmark? }, notes?, paymentMethod: "CASH" | "ONLINE", website }`. For delivery, send **either** `deliveryAreaId` (listed area: sets the fee and minimum) **or** `otherArea` (2-60 chars, the customer's own text when their area isn't listed: no fee, no minimum, no `deliveryAreaId` on the order; the address is stored as `"House .., Street, <otherArea> (area not listed)"` and staff confirm the fee by phone); both or neither is a 400.

**Pickup (`orderType`).** The body also carries `orderType: "DELIVERY" | "PICKUP"` (anything else is a 400). A `PICKUP` order is stored as `TAKEAWAY`, takes only `customer: { name, phone }` and ignores every delivery field (no area, address or fee). It is refused with 400 `PICKUP_UNAVAILABLE` when `SiteSettings.pickupEnabled` is off (delivery likewise when `deliveryEnabled` is off); staff cannot switch both off (400 `AT_LEAST_ONE_ORDER_TYPE`). `pickupMinOrderAmount` > 0 applies as a minimum subtotal (400 `BELOW_MINIMUM`). The public order status answers `orderType` and, for pickup only, `pickup: { addressEn, addressUr, mapUrl, noteEn, noteUr }` so the website can say where to collect; the status values themselves are unchanged. Abuse limit: 3 orders from one phone marked "not collected" within 90 days blocks that phone (same answer as the other limits).

Order of operations (`guestOrder.controller.ts` → `guestOrder.service.ts`):
1. **Honeypot first.** A non-empty `website` returns a normal-looking `201` (random link and code, `status: "RECEIVED"`) and creates nothing — before any validation or database work, so a bot gets no feedback. No CAPTCHA.
2. **Strict validation** (`guestOrder.validators.ts`, pure): unknown keys rejected at the top level, in `customer`, and inside each item/deal line; `clientRequestId` a UUID; `name` 2–60; `house` 1–60; `street` 2–120; `landmark` ≤ 100; `notes` ≤ 200; at most **40 lines** (items + deals), quantity **1–50**; no client price and no deal customization (the shared parsers' defaults). Text is normalised — control characters become spaces and whitespace collapses — so a name can't break a printed slip.
3. **Phone** (`common/phone.ts`): `03XXXXXXXXX`, `+923XXXXXXXXX` or `923XXXXXXXXX`, spaces and dashes ignored, stored as `03XXXXXXXXX`; otherwise 400 `BAD_PHONE`.
4. **Replay:** a `clientRequestId` that already exists returns the original answer (**200**, with the order's *current* status), counts toward no limit, and works even after ordering has closed. If the phone differs, or the id belongs to a non-guest order, it is **409** `REQUEST_ID_REUSED` — a status link is never handed to someone else. A true race (unique violation on `clientRequestId`) resolves to the same replay.
5. **Ordering open?** `orderingOpen` from `getOrderingState()` (the same `computeOrdering` the website's `/store` uses: switched on **and** a business day active) else 409 `ORDERING_CLOSED`. The area must exist and be active else 400 `BAD_AREA`.
6. `createOrder` is called with `source: ONLINE`, `type: DELIVERY`, `status: AWAITING_RECEPTION`, `customerId: null`, `paymentStatus` left at `PENDING` for CASH or `AWAITING_VERIFICATION` for ONLINE, `deliveryAddress` = `"House <house>, <street>, <area name>"` plus `"\nLandmark: …"` on a new line, the area's `deliveryFee`, `minSubtotal` (the area's minimum, if > 0), `maxTotal` = 200,000, `onlineOnly: true`, a **`publicId`** (16 random bytes, base64url, 22 characters — the status link) and a **`publicCode`** (5 characters from `23456789ABCDEFGHJKMNPQRSTUVWXYZ`; a unique-violation on the code is retried with a new one, up to 6 times).
7. **Limits, counted in Postgres** (so they survive deploys), checked inside `createOrder`'s transaction after its per-business-day advisory lock via a `guard` hook, so two simultaneous orders can't both slip under a limit: **per IP** 5 orders / 10 minutes and 30 / 24 hours (from `OrderClientIp`, a keyed HMAC of the IP — no raw IPs are stored); **per phone** 3 orders still `AWAITING_RECEPTION` and 10 / 24 hours. Exceeding any → **429** `{ code: "TOO_MANY" }`. (The 30-per-day IP limit is covered by unit tests only; the script exercises the 5/10-minute one.)

Response `201` (`200` on a replay): `{ publicId, publicCode, orderNumber, total, deliveryFee, paymentMethod, status }` — money as strings; `status` is the customer-facing one (`RECEIVED` for a new order). Every error body is `{ code, error }`: `ORDERING_CLOSED` (409), `BAD_PHONE`, `BAD_AREA`, `BELOW_MINIMUM` (+ `minOrderAmount`), `ITEM_UNAVAILABLE` (hidden online, deal-only, open-price, or an inactive/empty deal), `ORDER_TOO_LARGE` (total > 200,000), `BAD_REQUEST` (everything else) — all 400 — `REQUEST_ID_REUSED` (409) and `TOO_MANY` (429).

**`GET /api/online/orders/:publicId`** — public, the customer's status page. `Cache-Control: no-store`; a malformed or unknown id is the same `404 { code: "NOT_FOUND" }` (the shape is checked before any query). Built by `toPublicOrderStatus` (`publicOrderMapper.ts`) field by field from an explicit `select` — never by spreading a row:
`{ publicCode, status, cancelReason, payment: { method, state }, lines, subtotal, discount, deliveryFee, total, createdAt }`.
- **`status`** (`deriveCustomerStatus`, pure): `AWAITING_RECEPTION` → `RECEIVED`; an accepted order → `CONFIRMED`, or `PREPARING` when any item is `PREPARING`, or `READY` when every item is `READY`/`SERVED` (and **`ON_THE_WAY`** instead when a rider is assigned); `COMPLETED` → `DELIVERED`; `CANCELLED` → `CANCELLED` with `cancelReason` (the free text reception typed; null otherwise).
- **`payment.state`** (`derivePaymentState`): CASH → `NOT_REQUIRED`; ONLINE: verified → `PAYMENT_CONFIRMED`, rejected → `PAYMENT_PROBLEM`, awaiting with a proof on file → `PROOF_RECEIVED`, awaiting without → `WAITING_FOR_PAYMENT`.
- **`lines`**: items as `{ kind: "item", name, nameUr, size, addOns: [{ name, price }], quantity, lineTotal }` and deals as `{ kind: "deal", name, nameUr, quantity, lineTotal, contents: [...] }`. `subtotal` is summed with `Decimal`.
- **Never returned:** phone, address, notes, the customer's name, staff names or ids, the rider, `orderNumber`, or any internal id (deal-line ids are used only to group rows server-side). `publicOrderMapper.test.ts` seeds every such column with a sentinel and asserts none appears; `verify-guest-orders.ts` repeats it on a real order.
- The link is a bearer secret: anyone holding it can read the order's contents (not its contact details). Helmet's `Referrer-Policy: no-referrer` keeps it from leaking to other sites.

**`POST /api/online/orders/:publicId/payment-proof`** — public, `multipart/form-data`, one image in field `file`, ≤ 5 MB (`proofUpload`, memory storage). Only for an **ONLINE** order whose `paymentStatus` is still `AWAITING_VERIFICATION` and that is not `CANCELLED`/`COMPLETED` (else 409 `NOT_AWAITING_PAYMENT`); 404 `NOT_FOUND` for an unknown id; 400 for a file that isn't a real JPEG/PNG/WEBP, 413 over 5 MB. The image goes through `processProof` (`common/media/processImage.ts`): **never cropped** (a phone screenshot is tall and the amount could be anywhere), auto-rotated, metadata stripped, flattened onto white, fitted inside 1600 px, WebP at quality 82, plus a ≤ 480 px thumbnail. It is stored as a `PAYMENT_PROOF` asset and linked as `Order.paymentProofMediaId`; **a replacement deletes the earlier proof in the same transaction**. Emits `order:updated` to `pos-admin` so an open Incoming card refreshes. Returns `{ paymentState: "PROOF_RECEIVED" }`. Staff read it through `GET /api/pos/orders/:id/payment-proof` (§3.9).

**Routing and limits.** `routes/online.routes.ts` mounts `/guest-orders` and a public `/orders/:publicId…` router **before** the customer-accounts gate, which still guards only the account-based `POST /api/online/orders` (so with accounts off that route is a 404 while the status and proof routes work). The general 300 / 15 min limiter skips `/guest-orders` and `/orders`; they have their own in-memory limiters (§6). `CORS_ORIGIN` **must list the website's origins**, or the browser blocks the JSON POST's preflight (§6, §9).

**What staff see.** Every staff order payload now carries `customerName`, `customerPhone`, `deliveryAddress`, `deliveryFee`, `publicCode`, `paymentProofMediaId` and a `deliveryArea { id, nameEn, nameUr }` relation (`orderInclude`), so the frontend reads them from the Order when there is no `Customer` row (`AS_BUILT_FRONTEND.md`). The `order:submitted` socket payload gained `customerName` and `publicCode` (additive). `totalAmount` **includes** `deliveryFee`, so dashboards and reports count the fee as sales.

## 4. Business logic as implemented

### 4.1 Order creation

`createOrder` (`backend/src/modules/order/order.service.ts:157-338`) is the single entry point both the POS order-creation route and the online order-creation route call into.

1. Rejects an order with zero items **and** zero deals (`EmptyOrderError`).
2. Requires an active `BusinessDay` (`NoActiveBusinessDayError` otherwise) — every order is stamped with that day's id.
3. If `waiterId`/`riderId` given, each must reference an active `Employee` (`EmployeeNotFoundOrInactiveError`).
4. Every direct `menuItemId` is resolved through `resolveItemPrice(menuItem, variantId, unitPrice)`: if `menuItem.isOpenPrice`, `variantId` must be **absent** and `unitPrice` **required** — validated against `minPrice`/`maxPrice` when either is set (else `InvalidOrderItemsError`), and the line's `OrderItem.isCustomPrice` is set `true`. Otherwise, a client-sent `unitPrice` is **always rejected** (never silently ignored) and the existing rule applies: if the menu item has any priced variant, a `variantId` is **required** and must belong to that item and have a non-null price; if it has no priced variants, `variantId` must be **absent** and the item must have a non-null standalone `price`. This is what lets a sized item (e.g. pizza) be ordered at all, blocks a deal-only variant (e.g. Nuggets "5 pc") from being picked directly, and lets an open-price item (e.g. a custom cake) be ordered at whatever price the cashier types. The resolved `variantId`/`variantLabel` are snapshotted onto the created `OrderItem`, like `unitPrice`, so a later rename/price-change/delete of the variant never changes an already-placed order's line.
   `unitPrice` is only ever accepted on the line itself — shape-validated by `parseItemFields`/`parseOrderItems`'s `allowUnitPrice` option, which the POS routes (`order.controller.ts`'s `createOrder`/`addOrderItems`) pass as `true` and the online route (`payment.controller.ts`) leaves at its default `false`, so a customer-sent `unitPrice` 400s before `resolveItemPrice` is ever reached. A deal's customized contents (`parseDealCustomization`'s items) never allow `unitPrice` either way, and `resolveDealCustomizationVariant` separately rejects an `isOpenPrice` menu item outright — an open-price item can never be swapped/added into a deal's contents at order time, matching the deal-save-time rule below.
   Optional `addOnIds` on a line go through `resolveAddOns(menuItem, variantLabel, addOnIds, addOnById)`: each must reference an `AddOn` whose `categoryId` matches the menu item's `categoryId` **and** has an `AddOnPrice` for the line's resolved `variantLabel` (an unsized line — `variantLabel === null` — can never take an add-on, since `AddOnPrice.size` is never null); otherwise `InvalidOrderItemsError`. Duplicate `addOnIds` on one line are rejected at the `parseOrderItems` shape-validation stage. The resolved add-ons are summed into `unitPrice` (see step 5) and snapshotted as `[{ addOnId, name, price }, ...]` onto `OrderItem.addOns`, same reasoning as `variantLabel`.
5. **Totals**: `unitPrice` = the resolved base price (item or variant) **plus the sum of its add-ons' prices**, computed once at order time and never re-read live afterward by any print/display code; `subtotal = unitPrice × quantity`; deal lines priced from the live `Deal.price` (deal-exploded items don't currently support add-ons — out of scope for this step); `totalAmount = itemsTotal + dealLinesTotal - discount`, all in `Prisma.Decimal` arithmetic (never floats) — `order.service.ts:236-239`.
6. **Everything from here runs inside one `prisma.$transaction`** (`order.service.ts:243-333`):
   - Takes `SELECT pg_advisory_xact_lock(hashtext(businessDayId)::bigint)` — serializes concurrent requests for the *same business day* only (a different business day's orders aren't blocked by this lock).
   - Reads `MAX(orderNumber)` for that business day and uses `+1` — this read-then-write is safe only because of the advisory lock above; without it, two concurrent requests could both read the same max and collide (the lock is what prevents that, not the `@@unique` constraint, which would just turn a race into a 500 instead of silently succeeding twice).
   - Creates the `Order` row with nested `items: { create: ... }`.
   - **Deal explosion**: for each requested deal, creates one `OrderDealLine` then `createMany`s its composition as `OrderItem` rows at `unitPrice`/`subtotal` = `0`, linked via `dealOrderLineId`, with `kitchenId` copied from each exploded menu item. Two paths:
     - **Standard** (no `customization` on that deal entry — the only path before this step): composition is the deal's flat `DealItem` list (fixed `menuItemId`×`quantity`, no size, no add-ons). `OrderDealLine.unitPrice`/`subtotal` = the live `Deal.price`; `baseUnitPrice` = the same; `customization` = `null`.
     - **Customized** (POS-only — `deals[].customization`, staff-only; see §3.9's online-route note): the cashier's own `items` (each validated the same way a normal order line is — `resolveDealCustomizationVariant`/`resolveAddOns`, size/add-on rules identical to a direct line, except a deal-only item with no standalone price is allowed here) are exploded instead of the deal's standard contents and instead of anything choice-related. `OrderDealLine.unitPrice`/`subtotal` = the cashier's `finalPrice`; `baseUnitPrice` = the deal's standard `Deal.price` (so the owner can see what changed); `customization` = `{ reason?, items: [{ menuItemId, name, variantLabel?, quantity, addOns: [{ name, price }] }] }`, a readable snapshot of exactly what was charged for. The deal's own `quantity` must be `1` when customized — a customized deal is always its own line; ordering a second one means another cart entry. Inventory deduction (next bullet) covers these exploded items the same as any other.
     - `DealComponent` (choice-slot schema) is still unused by either path, same as before this step — see §3.9's `/api/pos/deals` note and §13's known-problems list.
   - **Inventory deduction**: `if (input.placedByStaffId !== undefined && input.status !== AWAITING_RECEPTION)` — staff-placed orders deduct immediately; an order created straight into `AWAITING_RECEPTION` (either source) never does, regardless of who placed it — see §4.1a. Online/customer orders otherwise never auto-deduct at creation either way, because `InventoryTransaction.performedById` is a required FK with no valid staff id to attribute it to.
7. **After the transaction commits**: if the order is `AWAITING_RECEPTION`, `emitNewOrderItemsByKitchen` is **skipped** and `order:submitted` is emitted to the `pos-admin` room instead (see §4.1a) — otherwise (every pre-existing case, unchanged) `emitNewOrderItemsByKitchen` fires unconditionally, grouping the order's items by `kitchenId` and emitting `order-item:new` to each `kitchen:<id>` room.

**Adding items to an existing order** (`addOrderItems`, `order.service.ts`) mirrors steps 4–6 above for the new items only, blocked if the order is `CANCELLED`/`COMPLETED` (`OrderClosedError`) **or still `AWAITING_RECEPTION`** (`OrderAwaitingReceptionError`, new — edit via `PUT /:id/submission` instead, see §4.1a), then increments `totalAmount`, deducts inventory for just the new items, and emits `order-item:new` for only the newly-added items (not the whole order again).

**Removing an item** (`removeOrderItem`, `order.service.ts`) only allows removing an item that is still `PENDING` (`OrderItemNotPendingError` otherwise — the kitchen has already started it) and isn't part of an exploded deal (`DealOrderItemError`); blocked if it would leave the order with zero items and zero deal lines (`EmptyOrderError` — "cancel instead"), or if the order is still `AWAITING_RECEPTION` (same new error as above). Decrements `totalAmount`, restocks inventory, **does not** emit any socket event (the kitchen was never told to remove it from its screen — a gap, see §11).

**Guest-checkout extensions to `createOrder`** (all optional; nothing changes for a call that omits them): `customerName`, `customerPhone`, `deliveryAreaId`, `deliveryFee`, `publicId`, `publicCode`, `paymentProofMediaId`, `clientIpHash` (written to `OrderClientIp`), **`onlineOnly`**, **`minSubtotal`**, **`maxTotal`**, and a **`guard(tx)`** hook that runs inside the creation transaction after the advisory lock.
- `totalAmount` is computed by `computeOrderTotal()` (`common/orderTotals.ts`): **items + deals − discount + `deliveryFee`**. The fee is stored on the order, and *every* code path that recomputes a total from lines now uses the same helper and adds it back — `acceptOrder` with a discount, `updateSubmission` (reception editing quantities), `updatePaymentStatus` with a discount, and `reviewOrderChange` — so a stored fee can't be silently dropped (before this, each of those recomputed from lines alone).
- `minSubtotal` is checked against the server-priced items + deals (before discount and fee) → `BelowMinimumError`; `maxTotal` against the priced total → `OrderTooLargeError`. A `guard` that throws aborts the order with nothing written (`OrderGuardRejectedError`).
- **`onlineOnly`** (in `buildOrderLines`): a direct item must be `isAvailableOnline`, `sellableAlone` and not open-price; a deal must be `isActive`, `isAvailableOnline` and have fixed `DealItem`s — else `ItemNotOrderableOnlineError`. This closes the gap where order creation never checked what the public menu hides. It is set by both the guest route and the account-based `POST /api/online/orders`; the POS routes and `updateSubmission` leave it off (reception may still adjust).

### 4.1d Audit trail (`OrderEvent`)

Every money- or trust-relevant action on an order writes one `OrderEvent` row through `recordOrderEvent` (`order/orderEvents.ts`), **inside the same transaction as the change** — the action and its record commit or roll back together. Rows are append-only; nothing updates or deletes them. `reason` is trimmed and cut to 200 characters (older paths such as a reception rejection accept longer text; the full text stays on the order). `before`/`after` hold only the fields the action changed, money as strings (`"550.00"`).

| Type | Written by | before → after |
|---|---|---|
| `CANCELLED` | `cancelOrder`, `cancelOwnAwaitingOrder`, an approved CANCEL change request, `markOrderNotCollected`, `cancelScheduledOrder` | `{status, paymentStatus, paid, totalAmount}` → `{status: CANCELLED, …}` — `before.paid` is what "cancelled after payment" means |
| `REJECTED` | `rejectOrder` (reception) | `{status, paymentStatus}` → same |
| `ACCEPTED` | `acceptOrder` | `{status}` → `{status, paymentMethod}` |
| `DISCOUNT_SET` | `createOrder` (a POS order placed with a discount), `updateSubmission`, `acceptOrder`, `updatePaymentStatus` — **only when the discount actually changes**, including back to 0 | `{discount, totalAmount}` → same |
| `PAYMENT_MARKED` / `PAYMENT_UNMARKED` | `updatePaymentStatus` (cash toggle), `verifyPayment` (online), `acceptOrder` of an online-paid order — only when `paymentStatus` changes | `{paymentStatus, paidAmount}` → `{paymentStatus, paidAmount, totalAmount}` |
| `ITEM_ADDED` / `ITEM_REMOVED` | `addOrderItems` / `removeOrderItem` | totals before → after, plus the line(s) as "2 × Zinger Burger (Large)" |

`actorId` is the staff member who did it (from the request's token); null only for an action nobody on staff did. Not recorded (no matching type): an approved EDIT change request, `rejectPayment` on the old online payment queue, scheduled release, guest proof uploads.

### 4.1e Discounts: cap, reason, attribution (phase 1, fix 4)

`order/discountPolicy.ts` (`checkDiscountChange`) is applied by **every path that sets `Order.discount`**: `createOrder` (POS `POST /orders` with `discount`), `updateSubmission` (`PUT /:id/submission`, reception), `acceptOrder` (`POST /:id/accept`) and `updatePaymentStatus` (`PATCH /:id/payment-status`, Confirm Payment). The approved EDIT change request keeps the order's discount and isn't a discount change. Rules, on the server-priced subtotal (items + deal lines, before delivery fee):
- **Only a change is checked.** Re-sending the discount the order already has (Confirm Payment pre-fills it) needs no reason and isn't re-capped.
- **Reason required** (`discountReason`, 1–200 characters after trimming) whenever the new discount is above 0 → 400 "A reason is required for a discount" / "The discount reason must be at most 200 characters". Setting it back to 0 needs none.
- **Cap**: anyone but `SUPER_ADMIN` may give at most `SiteSettings.maxDiscountPercentPosAdmin` % (default 20) of the subtotal → **403** "Discount above 20% needs a Super Admin". `SUPER_ADMIN` has no cap but is still held to "not more than the total" (400 `DiscountExceedsTotalError`) — which `createOrder` now checks too (it didn't before, so a create-time discount could store a negative total).
- **Attribution**: on every change (including back to 0) the order stores `discountById`, `discountAt`, `discountReason`, and a `DISCOUNT_SET` event records before → after amounts with the reason (§4.1d).
- The cap is part of `GET/PUT /api/pos/site-settings` (`maxDiscountPercentPosAdmin`, 0–100, 2 decimals); a `PUT` that includes it from anyone but `SUPER_ADMIN` → 403 "Only a Super Admin can change the discount cap". It is never on the public `/api/online/store`.
- **Dashboard**: `GET /reports/analytics` returns `discounts: { total, count, byStaff: [{ staffId, name, count, amount }] }` — discounts on the period's sales orders, grouped by `discountById` (`staffId: null`, name "Not recorded", for discounts set before attribution existed).

### 4.1b Per-line notes

A short kitchen instruction on one line of an order ("no onion", "extra spicy"). Stored on `OrderItem.notes` for a directly-ordered item (this column has existed since `init` and is reused here) and on `OrderDealLine.notes` for a whole deal line (added by `20261109120000_order_deal_line_notes`). A deal's exploded `OrderItem` rows never get their own note. They expose the deal line's note through `dealOrderLine.notes`, which every item payload includes (order detail, the kitchen queue, and both kitchen socket events), so the kitchen sees it under each component of the deal.

- **Validation** (`parseLineNote`, `order.service.ts`; limit `ORDER_LINE_NOTE_MAX_LENGTH = 100`). The value must be a string (or absent/`null`). It is trimmed, and more than 100 characters *after trimming* is a 400. Blank after trimming means "no note" and is stored as `null`, never `""`. The same function validates `items[].notes` and `deals[].notes` everywhere either can enter: POS create, the online create route, `POST /:id/items`, `POST /submit`, `PUT /:id/submission`, and an order taker's `EDIT` change request (validated at request time and re-parsed at approval). A deal note works on a plain line (it applies to every unit of a line with `quantity > 1`) and on a customized one.
- **Editing after placement**: two endpoints, `PATCH /:id/items/:itemId/notes` (`updateOrderItemNote`) and `PATCH /:id/deal-lines/:dealLineId/notes` (`updateOrderDealLineNote`), both POS_ADMIN/SUPER_ADMIN. The editable window is the same as adding or removing items: blocked when `CANCELLED`/`COMPLETED` (`OrderClosedError`, 400) and when `AWAITING_RECEPTION` (`OrderAwaitingReceptionError`, 409). An awaiting order's notes are edited with the rest of it through `PUT /:id/submission`. There is no item-status restriction: a note can still be corrected on a `READY`/`SERVED` item, as a record.
- **Kitchen notification**: every order these endpoints accept has already been sent to the kitchen, so a real change (not a no-op save of the same note) is pushed exactly like newly added items. The same per-kitchen grouping and payload shape go to the same `kitchen:<id>` rooms, under the event `order-item:note-updated` (see §5). It carries the changed item, or every item exploded from the changed deal line, with current `notes`/`dealOrderLine.notes`. Items already `SERVED` are left out, since they've left the kitchen. The emit is wrapped in `emitSafely`.
- **Not covered**: an approved order-taker `EDIT` change request (`reviewOrderChange`) still deletes and recreates every item without any kitchen emit. That was already true for its added and removed items before notes existed, so a note changed that way doesn't reach an open Kitchen Display until it reloads. See §13.

### 4.1c Scheduled orders (`SCHEDULED`)

A POS order can be placed "for later": `POST /orders` with `scheduledFor`. It is saved immediately (numbered, priced, items and notes stored) but **on hold** until that time. **Time rules** (`parseScheduledFor`): an ISO string with an explicit zone (`Z` or `±hh:mm`; the client converts the Pakistan time it showed), strictly in the future, at most `SCHEDULE_MAX_AHEAD_MS` (24 h) ahead, judged by the server clock. Times are stored as UTC instants; every screen shows Pakistan time.

**While `SCHEDULED`, nothing downstream sees the order:**
- **No stock deducted:** `createOrder` skips `deductForOrderItems`.
- **No socket emit at all:** no `order-item:new`, no `order:submitted`.
- **Not in Incoming orders:** that list is `AWAITING_RECEPTION` only.
- **Not in any kitchen queue:** `getKitchenQueue` excludes it like `AWAITING_RECEPTION`.
- **Not in sales:** excluded from dashboard sales, order count and top items (§4.7), and from the daily Excel's sales/order count, which gains a "Scheduled (not released) Count" row.
- **Nothing that would reach a kitchen or move stock:**
  - `OrderScheduledError`, 409: adding items, removing items, note edits, kitchen status changes.
  - `OrderNotAwaitingReceptionError`, 409: accept, reject, submission edit.
- **No printing:** the frontend hides its print buttons, and the browser-print fallback pages refuse to print it.
- **Still allowed:** assign (waiter, rider, table), cash payment-status, and the normal `PATCH /:id/cancel`.

**Release (the only way out of `SCHEDULED` into the live flow).** `transitionScheduledOrder` runs one transaction: `UPDATE "Order" SET status = AWAITING_RECEPTION, releasedAt = now WHERE id = ? AND status = SCHEDULED [AND scheduledFor <= dueBy]`, plus a read of the result.
- **Exactly once:** however many callers race — the job on several server instances, the startup pass, "Release now", ending the day — exactly one UPDATE matches. Only that caller emits `order:submitted` to `pos-admin`, which drives the existing chime, toast and Incoming refetch. Everyone else gets count 0: the job skips the order, and "Release now" answers 409.
- **After release it is an ordinary incoming order.** It shows in Incoming orders, queued by `releasedAt` rather than `createdAt` (`getIncomingOrders` sorts on `releasedAt ?? createdAt`). Reception's accept then notifies kitchens (`order-item:new`), deducts stock and prints slips ("Print and send") per the existing rules. `acceptOrder` now sends any non-online order to `PENDING`, so a released POS order starts where a directly placed POS order does. Online orders still go to `CONFIRMED`; the order-taker case is unchanged.
- **Why one transaction:** the read must see exactly what that call changed. Done as separate statements, concurrent calls on the local `prisma dev` database got each other's results (see §12).

**The release job** (`scheduledRelease.job.ts`, started from `server.ts` once the server is listening):
- **Schedule:** a pass runs immediately at startup (the catch-up for anything that fell due while the server was down — every deploy restarts it), then every `SCHEDULED_RELEASE_INTERVAL_MS` (30 s). An order goes out at most about 30 s after its time.
- **No in-memory state:** each pass asks the database (`status = SCHEDULED AND scheduledFor <= now`, indexed) and releases each due order with the conditional UPDATE above. Restarts lose nothing, and a second server instance can't double-release.
- **Failures:** a failed pass is logged and retried on the next tick, and passes never overlap. Each release is logged as `[scheduled] released order #N …`.

**Managing a scheduled order** (POS_ADMIN/SUPER_ADMIN, §3.9) — every action applies only while the order is still `SCHEDULED`, using the same conditional update, and 409s (`OrderNotScheduledError`) once it has been released:
- **List:** `GET /scheduled`.
- **Release now:** `POST /:id/release`.
- **Reschedule:** `PATCH /:id/schedule`, same time rules as create.
- **Edit items:** `PUT /:id/scheduled-items`. It reuses `replaceOrderContents`, now shared with `updateSubmission`; that helper re-checks the status inside its transaction with a conditional UPDATE, which also row-locks the order. A concurrent release either waits and then releases the edited contents, or wins and the edit 409s.
- **Cancel:** `POST /:id/cancel-scheduled`. Nothing to restock.

**Scope and business days:**
- **Who and which routes:** POS route only (POS_ADMIN/SUPER_ADMIN placing an order). The online and order-taker routes don't accept `scheduledFor`.
- **Business day:** an order belongs to the business day it was placed in. Ending that day is refused while any of its orders are still `SCHEDULED` (§4.4), so none can be released into a closed day where Incoming (scoped to the active day) would never show it.

### 4.1a Reception review (`AWAITING_RECEPTION`)

Added so that neither a waiter's dine-in order (a new `ORDER_TAKER` role) nor an online customer order reaches a kitchen or touches stock until a POS_ADMIN/SUPER_ADMIN ("reception") reviews it. All of this lives in `order.service.ts` alongside `createOrder`, reusing it rather than duplicating its pricing/validation.

- **`submitOrderTakerOrder`** — the body of `POST /api/pos/orders/submit`. Forces `type: DINE_IN`, `source: ORDER_TAKER`, `paymentMethod: CASH`, `status: AWAITING_RECEPTION`, `placedByStaffId` = the caller; no discount/waiter/rider/delivery fields accepted. Deal customization is allowed (same shared `parseOrderDeals({allowCustomization:true})` path), but the taker's own `finalPrice` is **never trusted** — `computeServerDealPrice` recomputes it server-side as standard + extras before handing off to `createOrder`. *Judgment call, flagged in the plan*: without the frontend-only "origin" (standard/swapped/added) bookkeeping the POS cashier's deal-customize dialog uses (it never reaches the server), this can't distinguish a swap from an add — it treats any quantity of a `menuItemId` beyond the deal's own standard count as "added" and charges its regular price for the excess. That's a simplification versus the richer POS-dialog rule (a pure swap there adds nothing), chosen because there's no `ORDER_TAKER`-facing UI yet to expose the difference, and because it errs toward not undercharging.
  **Duplicate-safe**: `clientRequestId` is checked against the DB first (`@unique` on `Order`) — an existing row for the same id, placed by the same caller, is returned as-is (200, not a new order); placed by someone else is a 409 (`ClientRequestIdConflictError`). A true concurrent-race duplicate hits the DB's unique constraint instead (`P2002`), caught and handled identically.
- **`updateSubmission`** — the body of `PUT /:id/submission`. 409 (`OrderNotAwaitingReceptionError`) unless the order is still `AWAITING_RECEPTION`. Replaces the order's contents wholesale — deletes every existing `OrderItem` (direct and deal-exploded) and `OrderDealLine`, then rebuilds from the new `items`/`deals` through the same pricing/explosion logic `createOrder` uses (factored out into an internal `buildOrderLines` helper both call), and recomputes `totalAmount` from scratch. An `ORDER_TAKER` may only edit their own order (404 on a mismatch, never 403) and, like submit, never gets a trusted deal-customization price — reception's edit does, plus it alone may also set `paymentMethod`/`discount` in the same call.
- **`acceptOrder`** — the body of `POST /:id/accept`, POS_ADMIN/SUPER_ADMIN. One transaction: 409 unless `AWAITING_RECEPTION`; an order that's `ONLINE`-sourced **and** `ONLINE`-paid requires `paymentVerified: true` in the body (else 400, `PaymentNotVerifiedError`) and sets `paymentStatus: VERIFIED` + `paymentVerifiedById`; sets `status` to what the order would have had if created directly today — `PENDING` for an `ORDER_TAKER` order, `CONFIRMED` for an `ONLINE` one; stamps `acceptedById`/`acceptedAt`; optional `paymentMethod`/`discount` override (discount recomputes `totalAmount` the same way `updatePaymentStatus` does, rejecting a negative result); deducts inventory exactly like `createOrder` does for a staff-placed order. After commit: `emitNewOrderItemsByKitchen` (the same function, now exported) pushes the items to their kitchen(s) — **this is the only way an `AWAITING_RECEPTION` order's items ever reach a kitchen** — plus `order:accepted` to `pos-admin` and, if the source is `ORDER_TAKER`, to `user:<placedByStaffId>`.
- **`rejectOrder`** — the body of `POST /:id/reject`, POS_ADMIN/SUPER_ADMIN. 409 unless `AWAITING_RECEPTION`. Sets `CANCELLED` + `cancelledReason`; sets `paymentStatus: REJECTED` iff `paymentRejected`. No restock — nothing was deducted. Emits `order:rejected` the same way.
- **`cancelOwnAwaitingOrder`** — the `ORDER_TAKER` branch of `PATCH /:id/cancel`. Only works while still `AWAITING_RECEPTION` and only on the caller's own order (404 otherwise); no restock, same reasoning as reject.
- **`getKitchenQueue`** gained `order: { status: { not: AWAITING_RECEPTION } }` in its `where` — without it, an `AWAITING_RECEPTION` order's `OrderItem` rows (real `PENDING` rows in the database; only the kitchen *emit* was skipped at creation) would reappear on a kitchen's screen after any plain REST refetch (`GET /api/pos/kitchen-queue` is a React-Query hook, not socket-driven — confirmed no `Order.status` awareness existed in this query before this change).
- **Socket emits new to this flow** (`order:submitted`, `order:updated`, `order:accepted`, `order:rejected`, `order:status`) all go through a small `emitSafely(fn)` wrapper that swallows a `getIO()` throw — needed so `backend/scripts/dev-fake-online-order.ts` (§9) can call `createOrder` directly with no live Socket.io server in that process, without that non-essential notification crashing an otherwise-successful write. Pre-existing emits (`order-item:new`/`order-item:updated`) are untouched by this and still throw if Socket.io isn't initialized, same as always.
- **`emitOrderStatusToTaker`**: fires `order:status { orderId, orderNumber, status }` to `user:<placedByStaffId>` whenever an `ORDER_TAKER`-sourced order is accepted, rejected, or cancelled. *Flagging, per the plan*: there is no derived/aggregate `Order.status` in this codebase (confirmed below, §4.2) — `IN_KITCHEN`/`READY`/`COMPLETED` are never set anywhere, so this event only ever fires for those three transitions, never for an "in kitchen"/"ready"/"completed" one, because those don't exist as `Order`-level transitions to fire it for.

### 4.2 Order and item status transitions

**`Order.status`** (`PENDING`/`CONFIRMED`/`IN_KITCHEN`/`READY`/`COMPLETED`/`CANCELLED`/`AWAITING_RECEPTION`) has **no state machine at all**. Grep of every place `Order.status` is ever written, across the whole backend:
- Created as `AWAITING_RECEPTION` (an `ORDER_TAKER` or `ONLINE` order — see §4.1a), `SCHEDULED` (a POS order with `scheduledFor` — §4.1c), or `PENDING` (every other POS order, default).
- Moved from `SCHEDULED` to `AWAITING_RECEPTION` only by `transitionScheduledOrder` (the job, "Release now"), and from `SCHEDULED` to `CANCELLED` by `cancelScheduledOrder` — both conditional on still being `SCHEDULED` (§4.1c).
- Set to `PENDING` or `CONFIRMED` by `acceptOrder` (§4.1a) — the only writer of those two statuses for a once-`AWAITING_RECEPTION` order.
- `verifyPayment` (`payment.service.ts`) **no longer writes `Order.status`** — it used to set `CONFIRMED`, which moved an order still at reception out of the Incoming inbox and into the kitchen queue with no accept and no stock deduction (§4.5).
- Set to `COMPLETED` by `completeOrder` (`POST /:id/complete`, paid orders from `PENDING`/`CONFIRMED`), by the POS-takeaway auto-complete in `updatePaymentStatus`, and by `markOrderDelivered` (`POST /:id/delivered`, from `PENDING`/`CONFIRMED`/`IN_KITCHEN`/`READY`) — all three through `completeInTransaction` (§4.2a).
- Set to `CANCELLED` by `cancelOrder` (only from `PENDING`/`CONFIRMED`/`AWAITING_RECEPTION`, conditional on the status it read — §4.3), an approved CANCEL change request (same rules), `rejectOrder`/`cancelOwnAwaitingOrder` (require `AWAITING_RECEPTION` first, §4.1a), `markOrderNotCollected` and `cancelScheduledOrder`. Every one of them now also sets `cancelledAt`/`cancelledById` and writes a `CANCELLED`/`REJECTED` event (§4.1d).
- **`IN_KITCHEN` and `READY` are still never set anywhere in the codebase.** They exist as valid enum values, are referenced by `businessDay.service.ts`'s `BLOCKING_STATUSES` and by the frontend's status filter and `StatusBadge`, but nothing ever transitions an order into them. In practice an accepted order stays `PENDING` (POS/accepted-taker) or `CONFIRMED` (accepted-online) until someone marks it delivered (`COMPLETED`) or it is cancelled.
- **`COMPLETED` is a finished, counted order everywhere**, checked for this change: the dashboard, the sales reports and the Excel export exclude only `CANCELLED`, `AWAITING_RECEPTION` and `SCHEDULED`, so a delivered order is counted exactly once (it's counted from the moment it is accepted and stays counted when it becomes `COMPLETED`); the Orders list filter, Order detail (`CLOSED_STATUSES`), `CLOSED_ORDER_STATUSES` (add/remove items) and `MyOrderCard` already treat it as closed; End Day does not block on it; and the order-taker's `deriveDisplayStatus` now maps it to "Served" (it used to fall through to the item statuses).

**`OrderItem.status`** (`PENDING`/`PREPARING`/`READY`/`SERVED`) *is* actively used — the Kitchen Display advances it — but the transition itself is **not validated**. `updateOrderItemStatus(itemId, status)` (`order.service.ts:587-599`) accepts any of the four enum values regardless of the item's current status; the only guard is that `status` be a legal enum member (checked in the controller) and, for a KITCHEN-role caller, that the item belongs to their own kitchen (403 otherwise). Nothing stops a request from jumping `PENDING → SERVED` directly or going backwards `SERVED → PENDING`. (The frontend's Kitchen Display only ever sends the "next" status per a fixed `PENDING→PREPARING→READY→SERVED` progression, but that's a UI convention, not a server-enforced rule.)

### 4.2a Completing an order (phase 2)

- **`completeInTransaction`** (`order.service.ts`) is the one completion write: a conditional `updateMany` to `COMPLETED` (so a concurrent cancel can't be overwritten), every item not yet `SERVED` → `SERVED`, and an `OrderEvent` `COMPLETED` with the actor and `after.via` = `complete` | `delivered` | `auto` (`after.auto: true` for the last). After commit, `afterCompleted` emits `order:updated` to `pos-admin`, `order:completed { orderId, orderNumber, itemIds }` to each kitchen room that still had unserved items (that kitchen's ids only), and `order:status` to the order taker.
- **Rule:** `POST /:id/complete` refuses an unpaid order (409 `UNPAID`). The POS turns that into one flow: "Complete order" on an unpaid cash order opens the Confirm Payment step first.
- **Auto-complete:** when `updatePaymentStatus` marks a **POS TAKEAWAY** order paid (it wasn't paid before, it is `PENDING`/`CONFIRMED`) and `SiteSettings.autoCompleteTakeawayOnPayment` is on (default; a missing settings row counts as on), it completes the order in the same transaction. Dine-in, online and order-taker orders never auto-complete. The switch is in `GET/PUT /api/pos/site-settings`; a `PUT` that includes it from anyone but `SUPER_ADMIN`/`POS_ADMIN` → 403.
- **Display status** ("In kitchen", "Ready", "Served") is derived from item statuses in the POS only; `IN_KITCHEN`/`READY` are still never written. `GET /api/pos/orders` now includes `items: [{ status }]` on each row for that.

### 4.3 Cancellation

**Staff cancel** — `cancelOrder` (`order.service.ts`), `PATCH /:id/cancel`, POS_ADMIN/SUPER_ADMIN (phase 1, fix 2):
- **Reason required**, 1–200 characters (controller, 400 otherwise). Stored in `cancelledReason`, with `cancelledAt` and `cancelledById`.
- **Status guard**: only `PENDING`, `CONFIRMED` or `AWAITING_RECEPTION` (`CANCELLABLE_STATUSES`). `COMPLETED` → 409 "Completed orders can't be cancelled"; `CANCELLED` → 409 "This order is already cancelled"; `SCHEDULED` → 409 (use `POST /:id/cancel-scheduled`). The write is a conditional `updateMany … where status = <status read>`, so a concurrent accept/deliver/cancel can't be overwritten (409 "This order just changed — reload it and try again") and the order row is locked for the rest of the transaction.
- **Paid orders** (`paymentStatus: VERIFIED` — cash marked paid or online verified): only SUPER_ADMIN/POS_ADMIN may cancel (403 otherwise — matters for the ORDER_TAKER path and the change-request path). The `CANCELLED` event records `before.paid: true`; reports read "cancelled after payment" from `status CANCELLED` + `paymentStatus VERIFIED` (§4.7). Cancelling never refunds anything — the frontend warns "Customer has paid — refund must be handled manually".
- **Restock** (`inventoryService.restockForCancelledOrder`, same transaction): reads the order's own stock ledger (`InventoryTransaction.relatedOrderId`) and, per inventory item, returns `STOCK_OUT − STOCK_IN` (so items removed earlier and approved edits are already netted out) as one `RESTOCK_CANCEL` row each, note "Returned: order cancelled". An order that never deducted stock — at reception and never accepted, scheduled and never released, placed by a customer with no staff to attribute it to — has no ledger rows and gets nothing. **Never twice:** if the order already has a `RESTOCK_CANCEL` row, nothing is done. The event's `after.restocked` says whether anything came back.
- **Kitchens told** (after commit): `order:cancelled` `{ orderId, orderNumber, itemIds }` to each `kitchen:<id>` room that has items from the order (that kitchen's ids only) — skipped for an order still at reception, which never reached a kitchen — and to `pos-admin` with all item ids. The Kitchen Display drops those cards. `order:status` to the order taker as before.

The **approved CANCEL change request** (`reviewOrderChange`) now goes through the same core (`cancelInTransaction`): status guard (409 for a completed order), restock, event, kitchen emit. Before, it cancelled with no restock and no kitchen notice.

The `ORDER_TAKER` path (`cancelOwnAwaitingOrder`, §4.1a) still requires `AWAITING_RECEPTION` and ownership and needs no reason; it also refuses (403) once reception has marked the order paid. It uses the same core, so it records who/when and its event (nothing to restock).

**Not collected** (`markOrderNotCollected`) cancels without restocking (the food was made) but now sets `cancelledAt`/`cancelledById` and sends `order:cancelled` so kitchens drop it. **Removing an item** (`removeOrderItem`) restocks that line (`STOCK_IN`, as before), records `ITEM_REMOVED`, and sends `order-item:removed` (same payload) to that item's kitchen and `pos-admin`.

### 4.4 Business day start/end, and "today"

There is **no calendar-date concept of "today" anywhere** in the backend. "The current business day" is defined purely as `prisma.businessDay.findFirst({ where: { isActive: true } })` (`businessDay.service.ts:6-8`) — whichever single row currently has `isActive: true`. This is the one and only definition used by order creation and the dashboard.

- **Start** (`POST /business-day/start`): 409 if one is already active (checked in the controller before calling the service). `label` defaults to today's Pakistan date (`karachiDate`, phase 1 — it was the UTC date); a display label only, never used in any query.
- **End — open orders listed (phase 2):** the 400 also carries `openOrders: [{ id, orderNumber, status, type, source, paymentMethod, paymentStatus, totalAmount, diningArea: { name } }]` (`getBlockingOrders`), so the End Day dialog can Complete or Cancel each one in place and then end the day normally.
- **End — unpaid orders (phase 1):** without `force`, besides the open-orders check below, any accepted order on the day that isn't marked paid (`UNPAID_ORDER_WHERE`, delivered ones included) also refuses with 400 `{ code: "UNPAID_ORDERS" (or "OPEN_ORDERS" when only open orders block), error, orderIds, unpaidOrders: [{ id, orderNumber, totalAmount, status, paymentMethod }], unpaidTotal }`. The frontend lists each unpaid order by number and amount before offering "End the business day anyway?" (which resends with `force: true`).
- **End** (`POST /business-day/end`): 404 if none active. **First, and regardless of `force`:** if any order on that business day is still `SCHEDULED`, 409 `{ error, code: "SCHEDULED_ORDERS_PENDING", scheduledOrders: [{ id, orderNumber, scheduledFor }] }`. The frontend offers to release or cancel them; an order left on hold would otherwise be released into a closed day and never appear in Incoming (§4.1c). Then, as before: Unless `force: true`, checks for any `Order` on that business day with status in `PENDING`/`IN_KITCHEN`/`READY`/**`AWAITING_RECEPTION`** (new — an order no one has reviewed yet would otherwise be stranded with no active business day left to be accepted into) and blocks (400, listing the offending order ids) if any exist. `force: true` skips that check entirely. **Ending a business day never touches any `Order` row** — it only flips `BusinessDay.isActive`/`endedAt`/`closedById`. A forced end leaves any open orders (including an unreviewed `AWAITING_RECEPTION` one) permanently attached to a now-closed day, with no automatic cancellation, completion, or reassignment anywhere in the codebase. **Blocking statuses** (without `force`): `PENDING`, **`CONFIRMED`** (new — an accepted online/guest order that hasn't been marked delivered; without it such orders were stranded after End Day), `IN_KITCHEN`, `READY`, `AWAITING_RECEPTION`. `COMPLETED` (delivered) and `CANCELLED` never block. The frontend's "end anyway?" prompt lists them.
- **Timezone (phase 1, fix 5)**: every day or month boundary is Pakistan time (Asia/Karachi, UTC+5, no DST) through `common/pkTime.ts` — no timezone library:
  - Reports, analytics and the monthly export bucket by the **Karachi date a business day opened** (`SQL_OPEN_DATE`, `karachiDate`) and the Karachi month of that date (`firstOfMonth`/`lastOfMonth`). A business day opened at 23:30 PK on Nov 30 (18:30 UTC) is November; one opened at 00:30 PK on Dec 1 (19:30 UTC on Nov 30) is December. (This was already true in code before phase 1; the UTC notes that used to be here were stale.)
  - `payroll.service.ts`'s `getCurrentMonthPayroll(now)` picks "this month" with `karachiYearMonth(now)` — a month runs 00:00 PK on the 1st to 00:00 PK on the next 1st. It used `getUTCMonth()`, so from 00:00 to 05:00 PK on the 1st it still showed the previous month.
  - Attendance dates are plain `YYYY-MM-DD` calendar dates (`@db.Date`, parsed as that date at UTC midnight), so the server never shifts them; the Attendance grid and the Reports page now default to the **Pakistan** date (`shopToday()` in the frontend) instead of the UTC one, which was yesterday's date until 05:00 PK.
  - `POST /business-day/start`'s default `label` is now `karachiDate(now)` (was the UTC date).

### 4.5 Online order and payment verification flow

`POST /api/online/orders/` (`payment.controller.ts:16-144`), customer JWT + `multipart/form-data` (screenshot upload):
1. `type` restricted to `TAKEAWAY`/`DELIVERY` (no `DINE_IN` — a comment notes that implies staff seated the customer, which only happens through the POS flow).
2. `DELIVERY` requires `customerAddressId`, and its ownership is re-verified server-side against the JWT's customer id (never trusted from the request body).
3. `items`/`deals` may arrive JSON-encoded as strings (multipart workaround alongside the file field) and are parsed before the shared `parseOrderItems`/`parseOrderDeals` validation.
4. `paymentMethod: ONLINE` requires a screenshot file; `paymentMethod: CASH` does not.
5. **Always creates `status: AWAITING_RECEPTION` now** (previously: `CONFIRMED` immediately for CASH, `PENDING` for ONLINE — that distinction moved to `acceptOrder`, see §4.1a). `paymentStatus` handling is unchanged: CASH stays at the schema default `PENDING`; ONLINE sets `AWAITING_VERIFICATION` and `paymentProofMediaId` (the screenshot, stored as a `PAYMENT_PROOF` media asset in Postgres — it used to be a file on local disk behind `paymentScreenshotUrl`, which Railway wipes on every redeploy; old rows keep their `/uploads/...` value).
6. `discount`/`waiterId`/`riderId` are never accepted from the client here — staff-only fields.
7. Delegates to the same `createOrder` as POS (§4.1), which — because the status is `AWAITING_RECEPTION` — skips the kitchen emit and inventory deduction, and emits `order:submitted` to `pos-admin` instead (§4.1a). An online order no longer reaches a kitchen or deducts stock until reception explicitly accepts it.

Verification (`payment.service.ts`), ONLINE_ADMIN/**POS_ADMIN**/SUPER_ADMIN (role list widened — reception reviews these too now):
- `verifyPayment`: requires current `paymentStatus === AWAITING_VERIFICATION` (`PaymentNotAwaitingVerificationError` otherwise); sets `paymentStatus: VERIFIED` and `paymentVerifiedById`. **It touches payment fields only — never `Order.status`, never the kitchen.** (Earlier it also set `status: CONFIRMED`, contradicting this very paragraph: a verified order left the Incoming inbox without reception accepting it and showed up in kitchen-queue reloads with no stock deducted. Fixed with guest checkout, where it would otherwise let a customer's order skip reception.) An order verified this way still needs `POST /:id/accept` (§4.1a) before a kitchen sees it; in practice, accepting an `AWAITING_RECEPTION` ONLINE-paid order usually happens via `accept`'s own `paymentVerified: true` path instead of this route first, but both are independently valid (this route only ever changes payment fields, `accept` is the only thing that can change `status` away from `AWAITING_RECEPTION`). **No socket event is emitted** by either — confirmed by grep, `payment.service.ts`/`payment.controller.ts` never call `getIO()`.
- `rejectPayment`: same precondition; sets **only** `paymentStatus: REJECTED` — `Order.status` is left exactly as it was, not auto-cancelled (use `POST /:id/reject` with `paymentRejected: true` for that, §4.1a). No customer-facing notification of any kind exists (no email/SMS/socket) — a human has to follow up by phone, matching the SRS's own stated assumption (§B.7) but worth noting there is zero system support for that follow-up either.

**Guest checkout** (`POST /api/online/guest-orders`, §3.19) is the account-free sibling of the flow above: the same `createOrder` and `AWAITING_RECEPTION`, with these differences.
- The customer identity is on the order (`customerName`/`customerPhone`/`deliveryAddress`/`deliveryAreaId`), the delivery fee is part of `totalAmount`, and the customer gets `publicId` (private status link) and `publicCode` (read out over the phone).
- **A payment-by-ONLINE guest order is placed first and its proof uploaded afterwards** (`POST /orders/:publicId/payment-proof`). Reception therefore can see one with nothing to verify, so `acceptOrder` refuses it (**400** `PROOF_MISSING`) until a proof exists — unless reception switches it to Cash in the same accept call. The Incoming card shows a warning and disables the accept buttons in that state.
- **Reception can accept either before or after `PATCH /payment/:orderId/verify`**: verification changes only `paymentStatus` (the status page then shows `PAYMENT_CONFIRMED` while the order is still `RECEIVED`), and `accept` with `paymentVerified: true` verifies on its own as before. Only `accept` moves the order on.
- Reception can still edit quantities on the card (`PUT /:id/submission`) and give a discount at accept; the delivery fee is kept through both (§4.1).
- After accept the flow is the ordinary kitchen flow; the status link follows the item statuses (`PREPARING`, `READY`), rider assignment (`ON_THE_WAY`) and `POST /:id/delivered` (`DELIVERED`). A reject becomes `CANCELLED` with the reason shown to the customer.

### 4.6 Inventory auto/manual deduction, vendor ledger, payroll

**Inventory** (`backend/src/modules/inventory/inventory.service.ts`):
- `deductForOrderItems`/`restockForOrderItems` (mirror functions) both filter `MenuItemInventoryLink` to `inventoryItem.trackingType === AUTO` only — a MANUAL-tracked item linked to a menu item is never touched by the order flow, by design.
- `adjustStock` (manual entry) rejects (400) any `InventoryItem` whose `trackingType !== MANUAL` — AUTO items can only ever move via the order hooks above, never by hand.
- `PUT /inventory/:id` explicitly rejects a `currentStock` field in the body — the only way to change stock is `adjustStock` (manual) or the order-driven auto hooks.
- `getLowStockItems` is a raw SQL query (`$queryRaw`) because Prisma can't compare two columns of the same row — `WHERE minThreshold IS NOT NULL AND currentStock < minThreshold`.

**Vendor ledger** (`vendor.service.ts`): a vendor's balance is **never stored** — `balanceFromEntries` sums `PURCHASE` entries as positive and `PAYMENT` entries as negative, computed fresh on every read (list and detail both). Ledger entries are append-only — no update or delete endpoint exists for a posted `VendorLedgerEntry`.

**Payroll** (`payroll.service.ts`): `upsertPayrollEntry`'s `remainingAmount` formula, recomputed and stored on every write (not computed on read):
```
remainingAmount = baseSalary + allowance - deduction - advanceTaken - paidAmount
```
Each of the five money fields independently falls back to the existing entry's value (or `employee.baseSalary` for `baseSalary`, `0` for the rest) if not supplied in the request — a partial update only overwrites the fields it mentions. `getCurrentMonthPayroll` synthesizes a **projected** (`id: null, isProjected: true`) row using the employee's live `baseSalary` for any active employee with no real entry yet for the current Pakistan month/year (`karachiYearMonth`, phase 1 — was UTC), so the UI can show "what they'd be owed" before any entry exists.

**Attendance**: `markAttendance` is a Prisma `upsert` keyed on the `@@unique([employeeId, date])` constraint — "one record per employee per day" is enforced purely by this upsert overwriting any existing record, not by rejecting a duplicate submission. There is no delete endpoint for an attendance record.

### 4.7 Dashboard and report queries, Excel export

**One definition** (`reports/salesDefinitions.ts`, phase 1, fix 3) — every figure below reads it, so none can drift:
- **Sales / orders** = orders whose `status` is not `CANCELLED`, `AWAITING_RECEPTION` or `SCHEDULED` **and** `paymentStatus = VERIFIED` (a CASH order staff marked paid — Confirm Payment sets `VERIFIED` — or an ONLINE order whose payment was verified), summed on `Order.totalAmount` (items + deals + delivery fee − discount). SQL: `SQL_COUNTED`; JS: `isSalesOrder`; Prisma filter: `SALES_ORDER_WHERE`.
- **Unpaid** = the same statuses but `paymentStatus <> VERIFIED` (open *or* delivered). Count and amount, shown on their own, **never added to sales**. `SQL_UNPAID` / `isUnpaidOrder` / `UNPAID_ORDER_WHERE`.
- **Cancelled** = `status CANCELLED`; **cancelled after payment** = cancelled and still `VERIFIED` (a cancel never unmarks payment). `SQL_CANCELLED` / `SQL_CANCELLED_PAID`.
- **Cash / online sales** = sales split on `paymentMethod`; **online orders** = sales with `source ONLINE`.
- **A day** = a `BusinessDay`, labelled by the Asia/Karachi date it opened (`SQL_OPEN_DATE`); a month = the Karachi calendar month of that date.

`fetchBusinessDayStats` aggregates all of these per business day in one SQL query. Before phase 1, sales counted every accepted, not-cancelled order whether paid or not; past orders were **not** changed, so past reports now show only their paid orders — `backend/scripts/report-unpaid-history.ts` (read-only) prints, per business day, old vs new sales and the unpaid orders that dropped out.

Places that used to compute sales without the shared definition, switched over in fix 3: the daily Excel summary (`orderReports.ts`, filtered on status only) and the dashboard's top items (`reports.service.ts`, a Prisma `groupBy` filtered on status only).

- **Dashboard** (`GET /reports/dashboard`): the single active business day (404 if none), from `fetchBusinessDayStats`: `totalSales`, `orderCount`, `cancelledCount`, `unpaidCount`/`unpaidAmount`, `cancelledAfterPaymentCount`/`cancelledAfterPaymentAmount`, `awaitingReceptionCount`, and the top 5 items by quantity among sales orders.
- **Analytics** (`GET /reports/analytics`, what the Dashboard page shows): `totals`/`previousTotals` carry `sales`, `orders`, `cancelledCount/Value`, `cancelledPaidCount/Value`, `unpaidCount/Value` and the rest; hourly, category, item and breakdown figures all filter on `SQL_COUNTED`.
- **Sales report** (`GET /reports/sales?from=&to=&groupBy=`): Karachi dates; `groupBy=day` → one row per business day; `groupBy=month` → those rows bucketed by the Karachi month of the day's opening date.
- **Excel export** (`exceljs`, `backend/src/common/excel/`):
  - `GET /api/pos/orders?export=xlsx` — the order list's own export (`buildOrdersWorkbook`), every row with its real status and payment status, no totals.
  - `GET /api/pos/reports/export?type=daily|monthly&businessDayId=` — `buildDailyReportWorkbook`: Summary (Order Count and Total Sales = sales orders only; Cancelled, Awaiting Reception and Scheduled counts; then **"Unpaid Count (not in sales)"** and **"Unpaid Amount (not in sales)"**) + Orders sheet. `buildMonthlyReportWorkbook`: the anchor business day's Karachi month, one row per business day from `fetchBusinessDayStats`.

  There is no export for the ad-hoc date-range `getSalesReport` view itself — only the two fixed `daily`/`monthly` types.

## 5. Real-time (Socket.io)

**Auth handshake**: two independent paths, branched on which handshake fields are present:
- **Staff**: `{ auth: { token } }` where `token` is the staff JWT. The server's `io.use` middleware verifies it with the same `JWT_SECRET` as HTTP auth and then (phase 1, fix 6) runs the same account check as `requireAuth` (`common/staffSession.ts`'s `checkStaffSession`): the `StaffUser` must exist, be active, and still have the token's role and kitchen. A refusal for any of these — or a missing/invalid/expired token — is an error whose `data` is `{ code: "AUTH" }` ("This account has been deactivated", "Your account was changed — please log in again", "Invalid or expired token"), which the POS treats like an HTTP 401. A database failure during the check refuses without that code (the client may retry). On success it sets `socket.staff` and `socket.data.staffId`.
- **Ending live sessions** (phase 1): `disconnectStaffSockets(staffId, reason)` (`config/socket.ts`) finds every socket with that `data.staffId` (`io.fetchSockets()`), emits `auth:revoked { reason }` to it, then disconnects it server-side. The staff controller calls it after `DELETE /staff/:id` ("Account deleted") and after a `PUT /staff/:id` that deactivates the account, changes its role or kitchen, or resets its password (`revokeReason`, compared against the row read before the update — a name change ends nothing). A failure here is logged and never fails the staff change.
- **Print agent**: `{ auth: { agentKey, printerId } }`. Checked first (before falling through to the staff path): rejects immediately if `PRINT_AGENT_KEY` is unset; otherwise constant-time-compares `agentKey` (SHA-256 digest + `crypto.timingSafeEqual`, to sidestep `timingSafeEqual`'s throw-on-length-mismatch); on match, sets `socket.printerId` instead of `socket.staff` and the socket never reaches the staff-only `"join"` handler at all (not just permission-checked out of it — structurally a different code path). A repeat connection for the same `printerId` evicts the old socket (`disconnect(true)`) rather than rejecting the new one, so a quickly-restarted agent isn't locked out by Engine.io's ~45s ping-timeout window before the old socket is noticed as dead. One registry (`registerPrintAgent`/`unregisterPrintAgent`/`getPrintAgentSocket`/`isPrinterOnline`, colocated in `socket.ts`) tracks at most one live socket per `printerId`; the unregister path is identity-checked (only clears the slot if it still holds *that* socket) so a losing socket from a rare simultaneous-reconnect race can't wipe out a newer registration when it disconnects. See `docs/PRINT_PROTOCOL.md` and §3's `print` endpoints for how a job actually gets dispatched to the registered socket.

**Rooms**: `"pos-admin"`, `"kitchen:<kitchenId>"`, and (new) `"user:<staffId>"` for staff. `canJoinRoom` (`socket.ts`): `SUPER_ADMIN`/`POS_ADMIN` may join `pos-admin` or any `kitchen:*` room; `KITCHEN` may only join its own `kitchen:${staff.kitchenId}`; every other role (`ONLINE_ADMIN`, and **`ORDER_TAKER`**) is forbidden from joining anything via the client-driven `"join"` event — this was already true for `ORDER_TAKER` by the function's own default-deny fallthrough before it existed as a role, confirmed by reading the function, not just assumed. A staff client must explicitly `emit("join", roomName, ackCallback)` after connecting to reach `pos-admin`/`kitchen:*` — nothing is auto-joined there. `user:<staffId>` is the one exception: an `ORDER_TAKER` socket is joined to its own `user:<id>` room **server-side**, unconditionally, in the connection handler itself — it never goes through (and can't reach) the `"join"` handler for this, so it structurally can't be made to join any other room either. A print-agent socket also joins `printer:<printerId>` on connect, but only for potential future admin-visibility tooling — job dispatch always targets the registered socket directly, never a room broadcast. **ONLINE_ADMIN may join `pos-admin` only** (listen-only, so its Incoming Orders badge and chime are live); kitchen rooms stay closed to it.

**Events emitted** (server → client), all from `order.service.ts`:
| Event | Emitted where | To | Payload |
|---|---|---|---|
| `order-item:new` | `emitNewOrderItemsByKitchen`, called after `createOrder` commits (non-`AWAITING_RECEPTION` only), after `addOrderItems` commits, and after `acceptOrder` commits (new) | each affected `kitchen:<id>` room | `{ orderId, orderNumber, type, diningArea, items: OrderItem[] }` — for `addOrderItems`/`acceptOrder`, `items` is only the newly-added/newly-accepted ones. Each item also carries `dealOrderLine: { dealName, customization, notes } \| null`, so a kitchen screen can show "Part of {deal}", whether it's customized, and the deal's note without a second query. |
| `order-item:note-updated` | `emitNoteUpdatedToKitchens`, after `updateOrderItemNote`/`updateOrderDealLineNote` actually change a note | each affected `kitchen:<id>` room | Same shape as `order-item:new`. `items` is only the item(s) whose note changed (for a deal line: every item exploded from it), excluding `SERVED` ones, each with its current `notes`/`dealOrderLine.notes` (`null` once removed). Wrapped in `emitSafely`. See §4.1b |
| `order:cancelled` | `cancelOrder`, approved CANCEL change request, `markOrderNotCollected` (phase 1) | each `kitchen:<id>` with items from the order (not for one still at reception) and `pos-admin` | `{ orderId, orderNumber, itemIds }` — a kitchen room gets only its own item ids |

| `order-item:updated` | `updateOrderItemStatus` | both `pos-admin` and `kitchen:<kitchenId>` | the full updated `OrderItem` row incl. `order: {id, orderNumber}` |
| `order:submitted` | `createOrder`/`submitOrderTakerOrder`, when the created order is `AWAITING_RECEPTION`; and the one winning release of a scheduled order (§4.1c) | `pos-admin` | `{ orderId, orderNumber, source, diningArea: {name} \| null, takerName: string \| null, itemCount, createdAt, scheduledFor }` (`scheduledFor` non-null only for a released scheduled order, whose `source` is `POS`). The five `order:*` events are new; each is wrapped in a small `emitSafely` helper that swallows a `getIO()` throw (unlike every pre-existing emit, which doesn't) — see §4.1a for why. No other backend module ever calls `getIO()` — confirmed by grep. Specifically: **payment verification/rejection and order-item removal still emit nothing.**

**Behavior on reconnect / missed-event recovery**: none exists. socket.io-client's default auto-reconnect is left unconfigured (server accepts whatever the default client behavior is), but there is no server-side event replay/versioning and no client-side re-fetch-on-reconnect (confirmed from the frontend side in the companion doc) — a dropped connection that reconnects will have silently missed any events that fired during the gap, with no mechanism to detect or recover that beyond a full page reload.

## 6. Auth and security

**JWT**:
- Staff: `{ id, role, kitchenId }`, signed with `JWT_SECRET`, `expiresIn: "12h"` (`auth.service.ts:30-34`).
- Customer: `{ id, type: "customer" }`, same secret, `expiresIn: "30d"` (`customer.service.ts:24-26`).
- No refresh-token mechanism anywhere — a token is either still valid or the user must log in again.
- ~~**A revoked/deleted `StaffUser` does not invalidate outstanding tokens.**~~ **Fixed** — `requireAuth` and the Socket.io handshake both check the account on every request/connection (see the next bullets, §5, phase 1 fix 6). Original note, for history: `requireAuth` only verified the JWT signature/expiry and the shape of its payload — it never re-checked the database. A token for a staff account that's since been deactivated or deleted keeps authenticating successfully until it expires; the only place this is detected at all is a narrow special case — a stale `placedByStaffId` surfacing as a foreign-key violation on order creation, which is specifically caught and turned into a 401 (`order.service.ts:630-637`) so the frontend's existing "session expired" handling kicks in. Every other authenticated action (viewing data, most writes) would simply keep working for a deactivated staff member until their token naturally expires.

**Passwords**: `bcrypt`, 10 rounds, both for `StaffUser` and `Customer`. **Staff** passwords created or reset through `POST /api/pos/staff`, `PUT /api/pos/staff/:id`, or `scripts/create-admin.js` must be at least 8 characters (`common/password.ts`, `MIN_PASSWORD_LENGTH`). Not enforced on login (existing shorter passwords keep working — they're hashed, so there's no way to list them) and **not** on customer signup (still only "non-empty"; password accounts are off by default, see below). No complexity rules.

**Client IPs behind Railway**: `app.set("trust proxy", TRUST_PROXY_HOPS)` (default `1`, `config/proxy.ts`). A hop **count**, not `true` — `true` trusts the client-controlled leftmost `X-Forwarded-For` entry, which would let anyone dodge every per-IP limit by forging the header; with `1`, Express uses the entry Railway's edge appended. Railway also sets `X-Real-IP`; that header isn't used. To confirm in production, set `LOG_CLIENT_IP=true`, hit `GET /health` once, and check the log line `[client-ip] req.ip=… x-forwarded-for=… x-real-ip=…` shows your real IP; then turn it off. If another proxy (e.g. Cloudflare) is ever put in front, raise `TRUST_PROXY_HOPS` by one. `config/proxy.test.ts` proves a forged leftmost entry is ignored at 1 hop.

**Customer accounts flag**: `ENABLE_CUSTOMER_ACCOUNTS` (default `false`). While off, `/api/online/auth/*`, `/api/online/addresses/*`, and `POST /api/online/orders` answer the standard `404 { error: "Not found" }` (`common/middlewares/customerAccountsGate.ts`, mounted in `routes/online.routes.ts`). `/api/online/menu`, `/deals`, `/health`, and the staff `/payment/*` routes are unaffected. Since `POST /api/online/orders` is the only upload route, uploads are unreachable while the flag is off.

| `kitchen` (write) | SUPER_ADMIN only; reads any staff |
| `menu`, `addon`, `deal`, `category` (reads) | any staff, incl. **ORDER_TAKER** (unchanged — these were already open to any authenticated staff before the role existed; confirmed by reading every route file, not assumed) |
| `menu` (write) | POS_ADMIN, SUPER_ADMIN (+ ONLINE_ADMIN for the online-availability toggle only) |

| `businessDay` `GET /current` | POS_ADMIN, SUPER_ADMIN, **ORDER_TAKER** (widened, read-only — see §3.15; needs to know whether a day is active before taking orders) |
| `diningArea` (write), `employee`, `businessDay` `POST /start`/`POST /end`, `vendor`, `inventory`, `reports` | POS_ADMIN, SUPER_ADMIN |
| `order` list/get/cancel | POS_ADMIN, SUPER_ADMIN, **ORDER_TAKER** (scoped to their own orders only — see §3.9/§4.1a) |
| `order` create/assign/payment-status/add-items/remove-item | POS_ADMIN, SUPER_ADMIN only (not ORDER_TAKER) |
| `order` submit/incoming/submission/accept/reject | see §3.9 — `submit`/`submission` (own order) is ORDER_TAKER; `incoming`/`accept`/`reject`/`submission` (any order) is POS_ADMIN/SUPER_ADMIN | **ONLINE_ADMIN additionally has `incoming`, `accept` and `reject` for `source: ONLINE` orders only** (404 for any other source; no discount) — added so it can review online orders from its own screen.

**`ORDER_TAKER` is default-deny everywhere else** — confirmed by reading every route file in the backend (not just grepping role lists): `staff`, `employee` (+ attendance/payroll), `inventory`, `reports`, `vendor`, `businessDay` writes, `order` create/assign/payment-status/items, and `kitchen-queue` all stay exactly as role-gated as before, with no accidental new access from adding the enum member (`requireRole`'s allowlist means a route only admits a role that's explicitly listed in that call).

**CORS**: single dynamic-origin callback (`app.ts`), driven by `CORS_ORIGIN` (comma-separated, `*` wildcard → regex), same logic reused for Socket.io's CORS config so the two can't drift apart. No credentials flag, no explicit methods/headers allowlist — defaults. **`CORS_ORIGIN` must include the customer website's origin(s)** (and any preview-deploy pattern): guest checkout is a JSON `POST` from the website's browser, which sends a CORS preflight — an origin that isn't listed gets every order blocked by the browser, with no error from the server. Note `https://www.example.com` and `https://example.com` are different origins.

**Rate limiting** (`express-rate-limit`, `common/middlewares/rateLimit.ts`): in-memory, per IP, per process — fine for these endpoints; order-placement limits are planned to live in Postgres in a later module. Every 429 is `{ code: "TOO_MANY", error: "Too many requests, please try again later" }` with `Retry-After` and standard `RateLimit-*` headers. Each limiter is its own counter:

| Limiter | Applies to | Limit | Counts |
|---|---|---|---|
| `staffLoginLimiter` | `POST /api/pos/auth/login` | 10 / 15 min / IP | failed attempts only (`skipSuccessfulRequests`) — the whole cafe likely shares one public IP |
| `customerAuthLimiter` | `POST /api/online/auth/signup` and `/login` (one shared bucket) | 10 / 15 min / IP | every request |
| `onlineGeneralLimiter` | everything under `/api/online` except `/payment/*` (staff-facing, same shared-IP reason) `/media/*` (counted by `mediaLimiter`), and `/guest-orders` + `/orders/*` (their own limiters below) | 300 / 15 min / IP | every request |
| `mediaLimiter` | `GET /api/online/media/:id` | 1000 / 15 min / IP | every request — a menu page legitimately loads dozens of images, so they get their own, larger budget |
| `guestOrderLimiter` | `POST /api/online/guest-orders` | 30 / 15 min / IP | every request — only blunts floods of *invalid* requests; the real per-IP / per-phone order limits are counted in Postgres (§3.19) |
| `proofUploadLimiter` | `POST /api/online/orders/:publicId/payment-proof` | 20 / 15 min / IP | every request |
| `orderStatusLimiter` | `GET /api/online/orders/:publicId` | 600 / 15 min / IP | every request — large because the website polls while a customer watches their order |

Counters reset on restart and aren't shared across replicas. Not rate limited: the rest of `/api/pos/*`, `/uploads`, Socket.io connections.

**Security headers**: `helmet` with its defaults (HSTS, `X-Content-Type-Options: nosniff`, `X-Frame-Options`, a default CSP, no `X-Powered-By`, …), **including `Cross-Origin-Resource-Policy: same-origin`**. Exactly two things opt out, each individually via `allowCrossOriginResource` / its own header: `/uploads` (the POS frontend on another origin shows payment screenshots) and `GET /api/online/media/:id` (the customer website shows photos). Everything else — all JSON — stays `same-origin`. CORS behaviour is unchanged.

**Body limits** (`app.ts`): JSON is capped at 100 KB globally and 50 KB under `/api/online` (the tighter parser is registered first). Oversize → `413 { error: "Request body too large" }`; malformed JSON → `400 { error: "Malformed JSON body" }` (both were a generic 500 before). Multipart uploads are limited separately (below).

**Input validation**: entirely hand-rolled per-controller `typeof`/enum-membership checks (no schema-validation library — no zod/joi/yup anywhere). Consistent in style across modules but duplicated by hand in every controller.

**Legacy disk upload (removed):** `config/upload.ts` (disk storage under `<cwd>/uploads`) was deleted — nothing writes to local disk any more. `/uploads` stays mounted (with the cross-origin opt-out, so the POS frontend can show them) only so the `paymentScreenshotUrl` of orders placed before this change still resolve; those files are gone after any redeploy. The account route's screenshot now goes to Postgres as a `PAYMENT_PROOF` asset like the guest one (§3.10).

**Media upload** (`backend/src/config/mediaUpload.ts`, §3.18) is a second, separate pipeline: multer **memory** storage (not disk), 8 MB limit, one `file` field, declared type must be JPEG/PNG/WEBP, and the real format is then checked by `sharp`. A rejected type is `400`; an oversize file is `413 { error: "File too large" }` (the shared error handler's message no longer names a size, since the two uploads have different limits). The same module also exports `proofUpload` (same pipeline, **5 MB**) used for customers' payment proofs — it goes through `processProof`, not the 4:3 photo crop (§3.19).

**Error handling**: a single catch-all Express error middleware (`common/middlewares/errorHandler.ts`, registered last in `app.ts`) maps upload rejections (400/413) and body-parser errors (413/400) to their proper status, and for anything else logs the error to console and returns a generic 500 `{error:"Internal server error"}`. No structured/external logging (no Winston/Pino/Sentry) — `console.log`/`console.error` only, including Socket.io connect/disconnect logs.

**Other risks worth flagging bluntly**:
- A deactivated/deleted staff account is rejected immediately on HTTP routes: `requireAuth` looks the account up on every request (one extra DB read) and answers 401 "This account has been deactivated" — and (phase 1) also 401 "Your account was changed — please log in again" when the account's role or kitchen no longer matches the token, so a demoted admin loses admin access at once. The Socket.io handshake runs the same check, and changing an account ends its live sockets at once (§5). **Still open:** a password reset does not invalidate HTTP tokens already issued (there is no token version on `StaffUser`); it does end the account's live sockets.
- Rate-limit counters are in-memory and per process: they reset on restart and aren't shared if the backend ever runs more than one replica.
- Only the mime type a client *declares* on an upload is checked; the file's bytes aren't inspected.
- Customer passwords still have no minimum length (only staff passwords got one), and existing staff accounts with passwords under 8 characters remain valid until reset.
- The rest of `/api/pos/*` (beyond staff login) has no rate limit — fine while it's staff-only behind JWTs, worth revisiting if that changes.

## 11. Data integrity risks

1. **Order cancellation doesn't restock inventory.** A cancelled order's stock deduction is never reversed — `currentStock` permanently understates true stock for every cancelled order that had AUTO-tracked items (§4.3).
2. **Forced business-day end orphans open orders.** `force: true` leaves `PENDING`/`IN_KITCHEN`/`READY` orders attached to a closed day with no automatic resolution; nothing in the codebase ever revisits them (§4.4).
3. **`Order.status` has no enforced lifecycle** — a COMPLETED/CANCELLED order can still be cancelled again; nothing ever reaches COMPLETED at all in the current code, so "is this order actually done" has no reliable signal beyond CANCELLED vs. not (§4.2). `AWAITING_RECEPTION`→accept/reject is the one lifecycle step that *is* now 409-guarded against repeating (§4.1a) — it just doesn't extend to anything after that point.
4. **`OrderItem.status` transitions are unvalidated** — any status can be set from any other via the API; a malicious or buggy client could set `SERVED` on a never-prepared item (§4.2).
5. ~~A deactivated/deleted `StaffUser`'s token is still accepted by the Socket.io handshake~~ **Fixed in phase 1 (fix 6)**: the handshake checks the account, and deactivating/deleting/re-roling an account disconnects its sockets at once (§5). Remaining: a password reset doesn't invalidate HTTP tokens already issued — see §6.
6. **Order-number collision is only prevented by an advisory lock being taken correctly inside the transaction** — if that code path were ever refactored to skip the lock (e.g. a future direct `prisma.order.create` bypassing `createOrder`), the `@@unique([businessDayId, orderNumber])` constraint would turn the race into a 500 rather than silently duplicating numbers, which is a safe failure mode but not a graceful one (no retry-on-conflict logic exists).
7. **Money precision**: consistently `Decimal(10,2)` server-side with no floating-point arithmetic anywhere in the backend — this specific risk is well-mitigated, called out here only for completeness per the task's own prompt.
8. **Concurrent item removal/addition on the same order**: `addOrderItems` and `removeOrderItem` each run their own separate `$transaction`, not a shared one — two simultaneous edits to the same order (e.g. two staff members both adding/removing items at once) are only serialized by Postgres's normal row-locking on the `Order` update, not by any application-level lock the way order-number assignment is. `(inferred)` this is probably fine under normal Postgres read-committed isolation for simple increment/decrement, but hasn't been stress-tested in code.
9. **Vendor delete doesn't guard its FK case** — deleting a vendor with existing ledger entries throws an uncaught 500 rather than the friendly 409 every other such endpoint gives (§3.13).

## 13. Known problems

- **Fixed with guest checkout:** order creation now enforces what the public menu offers (`onlineOnly`: online-available, sellable-alone, non-open-price items; active, online-available deals with fixed contents) on both online routes. Staff routes (POS, order-taker, reception edits) deliberately don't enforce it.
- **Payment proofs are in Postgres now.** Guest and account-route screenshots are `PAYMENT_PROOF` media (§3.19), so they survive redeploys. Orders placed *before* this change still point at `/uploads/...` files that are gone after any Railway redeploy.
- **Public rate limits and a server-rendered website.** If the website fetches `/store`, `/menu` or `/deals` from its own server, all visitors share one IP and the 300 / 15 min limit. The same goes for the **per-IP guest-order limit (5 per 10 minutes)**: many mobile users in Pakistan sit behind carrier-grade NAT and share one public IP, so legitimate customers can be refused — the per-phone limits are the sturdier control. If that bites, raise `GUEST_LIMITS.ipPerTenMinutes` (`guestOrderLimits.ts`).
- **The status link is a bearer secret in a URL.** Anyone who has it can read the order's contents (never its phone, address or notes) and, while the order awaits payment, upload a proof to it. It is 128 random bits, never cached (`no-store`), and not leaked through `Referer`.
- **Guest-order limits serialise with other order creation.** They are checked inside the create transaction under the per-business-day advisory lock, so they are exact but add a few queries to that lock window — fine at this volume.
- **`COMPLETED` is manual.** Nothing marks an order delivered automatically; staff press "Mark delivered" (`POST /:id/delivered`). Until they do, an accepted online/guest order is `CONFIRMED` and blocks a non-forced End Day.
- **A guest ONLINE order can wait indefinitely for its proof.** There is no timeout or reminder; reception sees "No payment proof uploaded yet" on the card and can reject it or switch it to Cash.
- **Delivery fees count as sales.** `totalAmount` includes the fee, so the dashboard and reports include delivery fees in sales (there is no separate delivery-revenue line).
- **Active-row caps are checked with a count inside a transaction, not a lock** — two simultaneous creates could each pass the check (admin-only, so unlikely).
- **`prisma migrate dev` can't be used against the local `prisma dev` server** (no shadow database). `20261110120000_public_site_content` was produced with `prisma migrate diff` and applied with `migrate deploy`. Separately, the `default` `prisma dev` instance cannot start while another process holds port 51213 (it was a VS Code language-server process during this work).


- **The local `prisma dev` database (PGlite) can mix up results under concurrent non-transactional statements.** While testing scheduled orders, six simultaneous `updateMany` + `findUnique` sequences got each other's results: wrong 404s and "bind message supplies 3 parameters" protocol errors. The same calls inside one interactive transaction were correct every time, which is why every scheduled-order transition runs in one (§4.1c). The existing single-`update` endpoints were unaffected in the same test. Production Postgres isn't expected to behave this way, but load or race tests against the local dev DB should be read with this in mind.

- **An approved order-taker edit never reaches the Kitchen Display live** (`reviewOrderChange`, `order.service.ts`). Approving an `EDIT` change request deletes and recreates every `OrderItem`/`OrderDealLine` with no kitchen emit. An open Kitchen Display keeps the old rows, including old notes, until it's reloaded. This predates per-line notes (§4.1b): the same is true for items added or removed this way.

- **TODO/FIXME/HACK comments**: none found anywhere in `backend/src` (confirmed by grep).
- **Dead/unused code**:
  - `backend/src/pages/PagePlaceholder.tsx` **(frontend)** — present but not imported by any route; see companion doc.
  - No backend-side dead exported functions were found after verification — one candidate (`buildOrdersWorkbook`) initially looked unused but **is** actually called, by `order.controller.ts:284` for the Orders list's own xlsx export (a separate code path from the reports module's daily/monthly exports, easy to miss on a narrow grep).
- **Duplicated logic**: the same three-line Prisma-error-code helper trio (`isNotFoundError`/`isUniqueConstraintError`/`isForeignKeyConstraintError`, checking P2025/P2002/P2003) is copy-pasted verbatim into at least 11 separate `*.service.ts` files (vendor, staff, payment, order, menu, kitchen, inventory, employee, diningArea, deal, customerAddress, customer, category) rather than shared from one location. Candidate for extraction into a single `backend/src/common/prismaErrors.ts`.
- **Inconsistency**: `vendor.controller.ts`'s `deleteVendor` doesn't catch the FK-conflict case the way every other delete-with-children endpoint does (§3.13, §11).
- **Frontend/backend shape disagreement**: none found beyond the `MenuItem.price` nullability fix already applied earlier this session (frontend's `MenuItem` type now correctly reflects `price: string | null`, matching the schema) — no other mismatches surfaced during this review.
- **`OrderSource.PHONE` and three `OrderStatus` values are effectively dead** — present in the schema/types/UI filters but never actually set by any code path (§4.2, §8).
- **`DealComponent`** (choice slots / variant-specific deal lines) has no CRUD API at all — only reachable via the one-off seed script, making any deal beyond a simple fixed-item combo unmanageable without re-running or hand-editing the seed.

## 14. Operational behavior (from code reading, not tested)

- **Internet drops mid-service**: no offline handling anywhere (confirmed §8). A staff member's browser would simply start failing API calls; React Query has no custom retry/offline config (default behavior). No queued/optimistic writes exist — a dropped connection during order creation either succeeds or the client sees an error; there's no "retry when back online" mechanism.
- **Server restarts**: `server.ts` has no graceful-shutdown handling (no `SIGTERM`/`SIGINT` listener, no draining of in-flight requests or open sockets) — a restart abruptly drops all active HTTP requests and Socket.io connections. Clients reconnect per their own default socket.io-client behavior but get no replay of anything missed (§5).
- **A kitchen display disconnects**: the socket's `connect_error` handler surfaces a visible banner telling the user to reload — there is no automatic re-fetch/re-sync on reconnect; local state silently drifts from the server until a manual reload (confirmed in the frontend companion doc).
- **A print fails**: entirely a browser/OS/printer-driver concern — `window.print()` has no success/failure callback the app can observe, so the app has no way to know or react to a failed physical print.
- **Two admins use the POS at once**: both see live kitchen-room/pos-admin-room socket events for item status changes; order creation is the only path with explicit serialization (the advisory lock, §4.1/§11); everything else relies on normal Postgres row-level locking, with no application-level optimistic-concurrency checks (no version column on `Order`) — a last-write-wins outcome is possible if two admins edit the same order's items at the same moment.
- **A business day is left open overnight**: nothing times it out or auto-closes it — it stays `isActive: true` indefinitely until someone explicitly ends it; order numbering and the dashboard continue scoping to it regardless of real elapsed time.

## Deviations from the SRS (`docs/SRS.md`)

The SRS is a planning document from before this project's build started; the implementation has diverged in several real ways:

1. **Architecture**: SRS §C.1 specifies "one backend, two frontends" — `zoryx-demo-pos-frontend` and `zoryx-demo-online-frontend`. **Only the POS frontend exists in this repo.** There is no customer-facing web app anywhere — `/api/online/*` is a fully-built API surface (customer auth, menu browsing, ordering, payment-verification admin) with **zero UI consumer**. Anyone using online ordering today would need a Postman-equivalent, not a browser.
2. **Folder structure**: SRS §D.1 proposes `src/routes/index.ts` (one file mounting both prefixes) and a per-module `order.socket.ts`; actual code uses two separate files (`pos.routes.ts`/`online.routes.ts`) mounted directly from `app.ts`, and all socket-emission logic lives inline in `order.service.ts`/`config/socket.ts` — no `order.socket.ts` exists. SRS also proposes `src/common/validators/`; actual validation is inline in every controller, no shared validators folder exists.
3. **Schema — deals**: the entire `Deal`/`DealItem`/`DealComponent` system, and the choice-slot/variant-component model, **does not exist in the SRS at all**. This is a substantial post-SRS schema addition.
4. **Schema — menu variants/add-ons**: `MenuItemVariant`, `AddOn`, `AddOnPrice`, and `MenuItem.price` nullability/`slug`/`sellableAlone` are **not in the SRS**. The SRS's `MenuItem.price` is a required `Decimal` with no sizing concept at all.
5. **Schema — vendor ledger**: `Vendor`/`VendorLedgerEntry`/`VendorLedgerEntryType` **do not exist in the SRS**. The entire vendor-purchase-ledger feature (SRS modules list FR-1 through FR-11 never mentions vendors/suppliers) was added later.
6. **Schema — `Order`**: SRS's `Order` model lacks `deliveryAddress` (added in a later migration) and lacks any `dealLines`/`OrderDealLine` relation. SRS's `OrderItem` lacks `dealOrderLineId`.
7. **Permission matrix** (SRS §B.2): "Reports & Excel export ... Online Admin ✅ (online orders only)" — **actual: `GET /api/pos/reports/*` is gated to POS_ADMIN/SUPER_ADMIN only**; there is no reports route anywhere under `/api/online/*`. ONLINE_ADMIN has zero access to any report.
8. **FR-1.1 phone orders**: the SRS lists "Phone" as one of four order-taking types. **Nothing in the actual code ever creates an order with `source: PHONE`** — it exists only as a schema enum value and a frontend filter option (§4.2/§8). There is no staff-facing "take a phone order" flow.
9. **FR-3.2 kitchen status progression**: the SRS describes items moving "Preparing → Ready" as part of a broader order lifecycle tracked via `Order.status` too. In practice `OrderItem.status` does progress through the Kitchen Display, but `Order.status` itself never advances past `PENDING`/`CONFIRMED` except to `CANCELLED` — `IN_KITCHEN` and `READY` are dead code, and `COMPLETED` is set only by the manual `POST /:id/delivered` (§4.2).
10. **What matches exactly, worth noting positively**: the core enum set (StaffRole, DiningAreaType, OrderType, OrderStatus, OrderItemStatus, PaymentMethod, PaymentStatus, InventoryTrackingType, InventoryTxnType, AttendanceStatus) is byte-for-byte identical to the SRS's proposed schema; the business-day-not-calendar-day rule, the forced-end-with-confirmation flow, the browser-based (not ESC/POS) thermal printing approach, the Decimal(10,2)-everywhere money convention, the server-side Excel export via `exceljs`, and the JWT-based role-checked-on-every-route auth model all match the SRS's stated intent closely.

### Order-taker change requests

`OrderChange` records every post-acceptance edit/cancellation request with requester, reviewer, immutable previous-state metadata, requested state, timestamps, and a status. An order taker may submit requests only for their own non-pending order; reception reviews them through `GET /api/pos/orders/changes/incoming` and `PATCH /api/pos/orders/changes/:changeId/review`. Approval is stale-checked against the order's `updatedAt`, cancellation is applied server-side, and item additions are repriced and inventory-checked by the existing order service.
